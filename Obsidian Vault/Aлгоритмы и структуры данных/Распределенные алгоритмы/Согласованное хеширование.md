**Согласованное хеширование (Consistent Hashing)** — это алгоритм хеширования, который позволяет минимизировать перераспределение ключей при изменении количества узлов (серверов) в распределенной системе.

Это фундаментальная технология для построения масштабируемых и отказоустойчивых распределенных систем.

---

### 1. Какую проблему оно решает?

Чтобы понять ценность согласованного хеширования, давайте посмотрим на **традиционный подход** (обычное хеширование по модулю).

#### Проблема обычного хеширования (`hash(key) % N`)
Представьте, что у вас есть кластер из `N` серверов. Вы хотите распределить данные (ключи) по серверам.
Формула: `Server = hash(key) % N`

*   **Сценарий:** У вас 10 серверов. Ключ `user_123` попадает на сервер `hash("user_123") % 10 = 3`.
*   **Проблема масштабирования:** Вы добавляете 11-й сервер. Теперь формула: `hash(key) % 11`.
*   **Результат:** Почти **все** ключи меняют свой сервер назначения.
    *   `hash("user_123") % 11` скорее всего не равно 3.
    *   Это означает, что при добавлении или удалении одного сервера вам нужно переместить ~90% данных между серверами. Это вызывает огромный сетевой трафик, простои и нагрузку на диски.

#### Решение: Согласованное хеширование
При добавлении или удалении узла меняется назначение только **K/N** ключей (где K — общее количество ключей, N — количество узлов). В идеале, при добавлении одного сервера, данные перемещаются только с одного соседнего сервера на новый. Остальные ключи остаются на своих местах.

---

### 2. Как это работает?

Вместо того чтобы хешировать ключи в диапазон `[0, N-1]`, мы хешируем их в огромное пространство, например, в кольцо от `0` до `2^32 - 1` (или `2^128` для MD5/SHA1).

#### Шаг 1: Хеш-кольцо (Hash Ring)
Представьте себе круг, где значения идут от 0 до максимума uint32.

#### Шаг 2: Размещение узлов
Каждый физический сервер (узел) также хешируется (по IP или имени) и помещается на это кольцо в определенную точку.
*   Server A -> позиция 100
*   Server B -> позиция 500
*   Server C -> позиция 900

#### Шаг 3: Размещение данных (ключей)
Ключ данных тоже хешируется и попадает в какую-то точку на кольце.
*   Key "user_1" -> позиция 300

#### Шаг 4: Поиск владельца (Clockwise Lookup)
Чтобы найти, где лежит ключ, мы двигаемся по кольцу **по часовой стрелке** от позиции ключа до первого встреченного узла.
*   Key "user_1" (300) движется по часовой стрелке. Первый узел — **Server B** (500). Значит, данные лежат на B.
*   Key "user_2" (800) движется по часовой стрелке. Первый узел — **Server C** (900). Данные на C.
*   Key "user_3" (950) движется по часовой стрелке. Проходит максимум кольца, зацикливается и попадает на **Server A** (100). Данные на A.

#### Что происходит при добавлении нового узла?
Добавим **Server D** на позицию 700.
*   Ключи, которые раньше шли к Server C (например, те, что были в диапазоне 500–900), теперь пересчитываются.
*   Ключи в диапазоне 500–700 всё еще идут к B.
*   Ключи в диапазоне **700–900** теперь будут попадать на **Server D** вместо C.
*   **Итог:** Только ключи из диапазона между новым узлом и предыдущим узлом по часовой стрелке должны быть перемещены. Все остальные ключи (например, те, что на A или в диапазоне 0–500 на B) не затрагиваются.
### Важные нюансы

1.  **Нагрузка на "соседа":**
    При удалении узла вся его нагрузка падает на *одного* соседа. Если у вас нет виртуальных узлов (vnodes), это может вызвать резкий скачок нагрузки (spike) на одном сервере, potentially приводя к его отказу (cascade failure).
    *   *Решение:* Использование виртуальных узлов (vnodes). При удалении физического узла удаляются все его виртуальные копии. Их нагрузка распределяется между *разными* соседями по кольцу, что сглаживает пик нагрузки.

2.  **Асинхронность и консистентность:**
    В распределенных системах  удаление узла не происходит мгновенно для всех клиентов.
    *   Пока одни клиенты уже знают, что D удален, другие могут продолжать слать запросы на D.
    *   Нужен механизм gossip-протокола или централизованного конфигурационного сервиса (как ZooKeeper/Etcd), чтобы все участники кластера имели актуальное представление о кольце.
### Сравнение: Добавление vs Удаление

| Действие            | Кто теряет данные?                               | Кто получает данные?                          | Объем миграции                                                    |
| :------------------ | :----------------------------------------------- | :-------------------------------------------- | :---------------------------------------------------------------- |
| **Добавление узла** | Предыдущий узел по часовой стрелке (Predecessor) | Новый узел                                    | Только ключи в диапазоне между новым узлом и его предшественником |
| **Удаление узла**   | Удаляемый узел                                   | Следующий узел по часовой стрелке (Successor) | Все ключи удаляемого узла                                         |

В обоих случаях затрагивается только локальная часть кольца, что делает алгоритм масштабируемым.

### 3. Проблема неравномерного распределения (Virtual Nodes)

В базовой версии есть проблема: если узлы расположены на кольце неравномерно, один сервер может отвечать за огромный сектор кольца, а другой — за маленький. Это приводит к дисбалансу нагрузки (hotspots).

**Решение: Виртуальные узлы (Vnodes)**
Вместо одного физического сервера мы создаем множество его "виртуальных копий" на кольце.
*   Server A имеет реплики: A1, A2, ..., Ak.
*   Каждая реплика хешируется отдельно и занимает свою позицию на кольце.

**Преимущества Vnodes:**
1.  **Балансировка:** Данные распределяются гораздо равномернее.
2.  **Плавное восстановление:** При выходе узла из строя его нагрузка распределяется не на один соседний узел, а равномерно среди всех остальных узлов (так как его виртуальные копии разбросаны по всему кольцу).

---

### 4. Где используется?

Согласованное хеширование является стандартом де-факто во многих распределенных системах:

1.  **Distributed Caches:**
    *   **Memcached:** Клиентские библиотеки (например, `libmemcached`) используют consistent hashing, чтобы знать, на какой ноде кэша искать ключ.
    *   **Redis Cluster:** Использует концепцию хеш-слотов (16384 слота), что является вариацией идеи разбиения пространства, хотя реализация немного отличается (fixed slots vs ring), но цель та же — минимизация перемещения данных.

2.  **Distributed Databases / Storage:**
    *   **Amazon DynamoDB:** Основа архитектуры Dynamo (и Cassandra, и Riak) построена на согласованном хешировании.
    *   **Apache Cassandra:** Использует token ring для распределения данных по нодам.
    *   **Couchbase:** Использует vBuckets, которые маппятся на ноды через consistent hashing.

3.  **Load Balancers:**
    *   Если вам нужно, чтобы запросы от одного и того же клиента всегда попадали на один и тот же бэкенд-сервер (sticky sessions), но при этом балансировщик должен устойчиво работать при добавлении/удалении серверов, используют consistent hashing по IP клиента.

4.  **CDN (Content Delivery Networks):**
    *   Для определения, на каком edge-сервере хранить или откуда отдавать контент.

### 5. Преимущества и Недостатки

#### Плюсы:
*   **Минимальная миграция данных:** При изменении состава кластера перемещается только небольшая часть данных.
*   **Горизонтальное масштабирование:** Легко добавлять и удалять узлы "на лету" без остановки системы.
*   **Децентрализация:** Не требуется центральный мастер-узел для маппинга ключей (клиент может вычислить расположение сам, если знает состав кольца).

#### Минусы:
*   **Сложность реализации:** Сложнее, чем простое `hash % N`. Нужно управлять кольцом, виртуальными узлами, обновлением конфигурации на клиентах.
*   **Наклон распределения (Skew):** Без виртуальных узлов распределение может быть очень неравномерным. Даже с виртуальными узлами требуется тщательный подбор их количества.
*   **Поиск соседа:** Поиск следующего узла по кольцу требует эффективной структуры данных (обычно отсортированный массив + бинарный поиск, или дерево, например, `std::map` в C++ или `bisect` в Python).
