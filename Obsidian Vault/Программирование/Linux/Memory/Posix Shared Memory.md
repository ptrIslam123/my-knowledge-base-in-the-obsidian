### Постановка задачи

- Есть **два процесса**, которые хотят коммуницировать между собой
- Они могут использовать для этого **разделяемую память**

### Механизм (как это должно работать)

1. **Первый процесс** аллоцирует страницу памяти
   - Страница оказывается в его адресном пространстве

2. **Второй процесс** подключает **ту же самую страницу** в своё адресное пространство

3. **Результат:**
   - То, что пишет первый процесс → видит второй
   - То, что пишет второй процесс → видит первый

> **Вопрос:** Такое возможно?

**Ответ:** Да.

---

### Проблема, которую нужно решить

Второй процесс должен **узнать**, какую именно страницу ему нужно загрузить (ту, которую использует первый процесс).

### Решение проблемы (способ идентификации)

Для того чтобы процессы "опознали" одну и ту же страницу, можно использовать **название файла (путь)**.

- Это приводит к концепции **маппингов страниц и файлов**

---
### Ключевая проблема: Идентификация

Представьте, что физическая память — это огромное складское помещение с миллиардами ячеек. Процесс А берет какую-то ячейку. Как процессу Б узнать номер именно этой ячейки? Просто так передать номер нельзя (из-за виртуальной памяти), да и номера эти динамические.

Для решения этой проблемы существует два семейства системных вызовов, которые предлагают **разные типы идентификаторов**.

---

### Способ 1: Идентификация через имя файла (POSIX / `mmap`)

Этот способ полностью соответствует вашей догадке про "название файла (путь)".

**Как это работает:**
Вы создаете "объект" в специальной псевдо-файловой системе (`tmpfs`), которая смонтирована в `/dev/shm`. У этого объекта есть **имя (путь)**.

*   **Процесс А** вызывает `shm_open("/my_shared_memory", O_CREAT | O_RDWR, 0666)`. Этим он создает объект с именем `/my_shared_memory` в `/dev/shm`.
*   Затем он вызывает `ftruncate()`, чтобы задать размер, и `mmap()` с флагом `MAP_SHARED`, чтобы отобразить этот объект в свою память.
*   **Процесс Б** вызывает `shm_open("/my_shared_memory", O_RDWR, 0666)`, используя **точно такое же имя**.
*   Затем процесс Б вызывает `mmap()` с `MAP_SHARED` для полученного файлового дескриптора. Ядро "понимает", что оба процесса ссылаются на один и тот же объект в `/dev/shm`, и подсовывает им одну и ту же физическую память.

**Итог:** Обмен данными работает. Это современный, рекомендуемый способ.

---

### Способ 2: Идентификация через числовой ключ (System V / `shmget`)

Это более старый способ, который тоже использует файловый путь, но более сложным путем. Он отвечает на ваш вопрос: *"есть еще такой подход с тем чтобы использовать какие нибудь другие идентификаторы для страниц памяти?"*

**Да, есть. Это числовой `key_t`.**

**Как это работает:**
Здесь используется не прямой путь, а **числовой ключ (`key_t`)**, который обычно получают с помощью функции `ftok()`.

*   `ftok()` принимает путь к **реально существующему файлу** на диске и число-проект, и генерирует на их основе уникальный числовой ключ.
    ```c
    key_t my_key = ftok("/home/user/common_file.txt", 'A');
    ```
*   **Процесс А** вызывает `shmget(my_key, size, IPC_CREAT | 0666)`, создавая сегмент разделяемой памяти, связанный с этим ключом.
*   **Процесс Б** вызывает `shmget(my_key, size, 0666)`, используя **тот же самый ключ**.
*   Если оба процесса сгенерировали одинаковый ключ (а они это сделают, если `ftok` получит одинаковые входные данные), `shmget` вернет им один и тот же идентификатор сегмента (`shmid`), а `shmat()` подключит их к одной физической памяти.

**Почему так сложно?**
Система V создавалась раньше, чем идея "все есть файл" стала доминирующей. Файл в `ftok` нужен только как статическая точка отсчета для генерации уникального числа.

---

### Способ 3: Идентификация через наследование (Анонимная память)

Это особый случай для связи **"родитель-ребенок"** после вызова `fork()`. Здесь процессы **уже знают** общую страницу, потому что один породил другого.

**Как это работает:**
*   Процесс-родитель вызывает `mmap(NULL, size, PROT_READ | PROT_WRITE, MAP_SHARED | MAP_ANONYMOUS, -1, 0)`.
*   Флаг `MAP_ANONYMOUS` говорит: "не привязывайся ни к какому файлу, просто выдели чистую память".
*   Флаг `MAP_SHARED` говорит: "сделай эту память разделяемой".
*   Затем родитель вызывает `fork()`. Система копирует **таблицы страниц** процесса. В результате и родитель, и ребенок получают **указатели на одни и те же физические страницы** памяти.

**Итог:** Никаких файлов, никаких ключей. Но работает только для процессов, связанных родством (один создал другого). Случайные процессы так соединить нельзя.

### Сравнительная таблица: как процесс Б узнаёт, что нужно подключиться?

| Способ | Что используется как "идентификатор"? | Как процесс Б его узнаёт? | Когда использовать |
| :--- | :--- | :--- | :--- |
| **POSIX (`shm_open` + `mmap`)** | **Имя** (строка, например `"/my_data"`) | Заранее договариваются об имени строки. Это очевидно и просто. | **Современный стандарт.** Любой IPC между разными процессами. |
| **System V (`ftok` + `shmget`)** | **Ключ** (`key_t`, целое число) | Оба процесса вызывают `ftok()` с одним и тем же путем к файлу и числом, чтобы получить одинаковый ключ. | Поддержка старого кода. Считается устаревшим. |
| **Анонимный (`mmap` + `MAP_ANONYMOUS`)** | **Наследование** (виртуальный адрес) | Никак. Ребенок автоматически наследует от родителя при `fork()`. | Только для связи родитель-ребенок в одном запуске программы. |

## Конспект: Три режима использования `mmap`

### 1. Простая (неразделяемая) аллокация памяти

`mmap` может выделять память, которую **не разделяют** другие процессы.

- Аналог `malloc()`, но на уровне страниц
- Обычно используется с `MAP_PRIVATE | MAP_ANONYMOUS`
- Другие процессы её не видят

Согласно `man mmap`, флаг `MAP_ANONYMOUS` (или его синоним `MAP_ANON`) создаёт отображение, не привязанное ни к какому файлу, а его содержимое инициализируется нулями[](https://man7.org/linux/man-pages/man3/mmap64.3.html). `MAP_PRIVATE` делает изменения в этой области памяти приватными для процесса, то есть они не будут видны другим процессам и не будут записаны обратно (что в случае анонимной памяти и не нужно)[](https://browse.library.kiwix.org/content/stackoverflow.com_en_all_nopic_2022-07/questions/33034831/difference-between-map-private-and-map-shared-in-mmap-for-threads)[](https://android.googlesource.com/kernel/common/+/2cc3c4b3c2e9c99e90aaf19cd801ff2c160f283c/Documentation/admin-guide/mm/nommu-mmap.rst). Это действительно эффективный способ выделить память, особенно для больших алокации.


```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/mman.h>
#include <unistd.h>

int main() {
    // 1. Выделяем память с помощью mmap
    // NULL: ядро само выбирает адрес для отображения
    // 4096: запрашиваем ровно одну страницу памяти (размер страницы по умолчанию)
    // PROT_READ | PROT_WRITE: разрешаем чтение и запись
    // MAP_PRIVATE | MAP_ANONYMOUS: создаем приватное, не связанное с файлом, отображение
    // -1 и 0: файловый дескриптор и смещение не используются из-за MAP_ANONYMOUS
    void* ptr = mmap(NULL, 4096, PROT_READ | PROT_WRITE, MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    if (ptr == MAP_FAILED) {
        perror("mmap failed");
        return 1;
    }

    // 2. Работаем с выделенной памятью как обычно
    // Согласно документации, содержимое страницы инициализируется нулями [citation:3][citation:7].
    printf("До записи: '%s'\n", (char*)ptr);

    const char* message = "Hello from private memory!";
    strcpy((char*)ptr, message);
    printf("После записи: '%s'\n", (char*)ptr);

    // 3. Освобождаем память
    if (munmap(ptr, 4096) == -1) {
        perror("munmap failed");
        return 1;
    }
    return 0;
}
```

### 2. Разделяемая память (IPC)

`mmap` может выделять память, которую **разделяют** несколько процессов.

- Используется `MAP_SHARED`
- Процессы видят изменения друг друга
- Идентификатор: имя файла или наследование

Для неродственных процессов **обязательно нужен именованный объект**. Есть два подхода:

- **POSIX (`shm_open` + `mmap`):** Это современный и предпочтительный способ[](https://ipfs.io/ipfs/QmXoypizjW3WknFiJnKLwHCnL72vedxjQkDDP1mXWo6uco/wiki/Mmap.html)

Работает он так:
1. Процесс А создаёт _объект разделяемой памяти_ с уникальным именем (например, `/my_shared_memory`) через `shm_open()`[](http://linuxman7.org/linux/man-pages/man3/shm_open.3.html) . Этот вызов возвращает файловый дескриптор. 
2. Затем процесс А использует `mmap()` с `MAP_SHARED` для отображения этого дескриптора в свою память[](http://linuxman7.org/linux/man-pages/man3/shm_open.3.html)
3. Процесс Б делает то же самое: вызывает `shm_open()` с **тем же самым именем** и `mmap()`. Ядро связывает их вместе.

**Анонимная память (`MAP_ANONYMOUS | MAP_SHARED`):** **Работает только для родственных процессов (после `fork()`)**[](https://mail.python.org/pipermail/python-list/2008-February/509003.html)
[](https://stackoverflow.com/questions/5656530/how-to-use-shared-memory-with-linux-in-c/5656561#5656561). 

#### Разделяемая память для родственных процессов (`fork`)

```c
// shared_parent_child.c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/mman.h>
#include <unistd.h>
#include <sys/wait.h>

int main() {
    // 1. Создаем анонимную разделяемую память ДО fork()
    //    Флаги MAP_SHARED | MAP_ANONYMOUS — ключ к успеху для этого сценария
    void* shared_ptr = mmap(NULL, 4096, PROT_READ | PROT_WRITE,
                            MAP_SHARED | MAP_ANONYMOUS, -1, 0);
    if (shared_ptr == MAP_FAILED) {
        perror("mmap");
        exit(1);
    }

    // 2. Создаем дочерний процесс
    pid_t pid = fork();
    if (pid == -1) {
        perror("fork");
        exit(1);
    }

    if (pid == 0) {
        // Код дочернего процесса
        printf("Child: Читаю: '%s'\n", (char*)shared_ptr);
        strcpy((char*)shared_ptr, "Привет от ребенка!");
        printf("Child: Записал: 'Привет от ребенка!'\n");
        munmap(shared_ptr, 4096);
        exit(0);
    } else {
        // Код родительского процесса
        // Сначала пишем что-то в память
        strcpy((char*)shared_ptr, "Сообщение от родителя");
        printf("Parent: Записал: 'Сообщение от родителя'\n");

        // Ждем немного, чтобы ребенок успел прочитать и перезаписать
        sleep(1);

        // Читаем, что записал ребенок
        printf("Parent: Читаю после ожидания: '%s'\n", (char*)shared_ptr);

        // Ждем завершения дочернего процесса
        wait(NULL);
        munmap(shared_ptr, 4096);
    }
    return 0;
}
```


#### Разделяемая память для неродственных процессов (POSIX)

Этот пример состоит из двух программ, которые обмениваются данными через именованный объект в `/dev/shm`. Это именно то, что вы описали как "современный и предпочтительный способ".

**Процесс "писатель" (создает объект и пишет):**

```c
// posix_writer.c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <fcntl.h>
#include <sys/mman.h>
#include <unistd.h>

#define SHM_NAME "/my_shared_data" // Имя должно начинаться с '/'
#define SHM_SIZE 4096

int main() {
    // 1. Создаем (или открываем) объект разделяемой памяти
    int shm_fd = shm_open(SHM_NAME, O_CREAT | O_RDWR, 0666);
    if (shm_fd == -1) {
        perror("shm_open");
        exit(1);
    }
    
    // 2. Устанавливаем размер (обязательно!)
    if (ftruncate(shm_fd, SHM_SIZE) == -1) {
        perror("ftruncate");
        exit(1);
    }
    
    // 3. Отображаем объект в память процесса
    void* ptr = mmap(NULL, SHM_SIZE, PROT_READ | PROT_WRITE, MAP_SHARED, shm_fd, 0);
    if (ptr == MAP_FAILED) {
        perror("mmap");
        exit(1);
    }
    
    // 4. Пишем данные
    sprintf((char*)ptr, "Hello from POSIX writer!");
    printf("Writer: записал '%s'\n", (char*)ptr);
    
    // Для демонстрации ждем, пока читатель прочитает
    printf("Writer: нажмите Enter для завершения...\n");
    getchar();
    
    // 5. Очистка
    munmap(ptr, SHM_SIZE);
    close(shm_fd);
    shm_unlink(SHM_NAME); // Удаляем объект из системы
    return 0;
}
```

**Процесс "читатель" (подключается к существующему объекту):**

```c
// posix_reader.c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <fcntl.h>
#include <sys/mman.h>
#include <unistd.h>

#define SHM_NAME "/my_shared_data"
#define SHM_SIZE 4096

int main() {
    // 1. Открываем существующий объект (без флага O_CREAT)
    int shm_fd = shm_open(SHM_NAME, O_RDWR, 0666);
    if (shm_fd == -1) {
        perror("shm_open");
        printf("Убедитесь, что процесс-писатель уже запущен и создал объект.\n");
        exit(1);
    }
    
    // 2. Отображаем память (ftruncate для читателя НЕ нужен)
    void* ptr = mmap(NULL, SHM_SIZE, PROT_READ | PROT_WRITE, MAP_SHARED, shm_fd, 0);
    if (ptr == MAP_FAILED) {
        perror("mmap");
        exit(1);
    }
    
    // 3. Читаем данные
    printf("Reader: прочитал '%s'\n", (char*)ptr);
    
    // 4. (Опционально) Пишем ответ
    sprintf((char*)ptr, "Reply from reader!");
    printf("Reader: записал ответ\n");
    
    // 5. Очистка (не удаляем объект, это делает писатель)
    munmap(ptr, SHM_SIZE);
    close(shm_fd);
    return 0;
}
```

### 3. Маппинг в имя файла

#### 3.1. Маппинг в виртуальный файл

`mmap` может привязать страницу памяти к **имени файла**, который физически не существует на диске.

- Файл создаётся в псевдо-ФС (`tmpfs`, например `/dev/shm`)
- Данные живут в ОЗУ, но имеют имя
- При перезагрузке исчезают

#### 3.2. Маппинг в реально существующий файл на диске

`mmap` может привязать страницу памяти к **обычному файлу на диске** (HDD/SSD).

- Изменения памяти → изменяют файл (с некоторой задержкой или через `msync`)
- Позволяет работать с огромными файлами, не загружая их целиком
- Используется в базах данных, редакторах видео


Это называется "file-backed mapping" — отображение, поддерживаемое файлом[](https://ipfs.io/ipfs/QmXoypizjW3WknFiJnKLwHCnL72vedxjQkDDP1mXWo6uco/wiki/Mmap.html)
- Вы открываете обычный файл на диске с помощью `open()`.
- Передаете этот файловый дескриптор в `mmap` с флагом `MAP_SHARED`.
- После этого чтение и запись в память — это чтение и запись в файл. Ядро само заботится о синхронизации (можно форсировать её вызовом `msync`).[](https://ipfs.io/ipfs/QmXoypizjW3WknFiJnKLwHCnL72vedxjQkDDP1mXWo6uco/wiki/Mmap.html)
- Огромный плюс в том, что файл может быть больше доступной оперативной памяти, и ядро будет подгружать нужные части "на лету" (demand paging).

### 3.1. Маппинг в виртуальный файл (`tmpfs`, `/dev/shm`)

Этот пример похож на POSIX разделяемую память, но с одним отличием: создается именно файл в `tmpfs`, который затем отображается в память.

```c
// file_virtual.c - Отображение файла в tmpfs (ОЗУ)
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <fcntl.h>
#include <sys/mman.h>
#include <unistd.h>

#define TMPFS_FILE "/dev/shm/my_virtual_file" // Файл в ОЗУ
#define FILE_SIZE 4096

int main() {
    // 1. Создаем/открываем файл в tmpfs
    int fd = open(TMPFS_FILE, O_CREAT | O_RDWR, 0666);
    if (fd == -1) {
        perror("open");
        exit(1);
    }
    
    // 2. Устанавливаем размер файла (обязательно для новых файлов для mmap)
    if (ftruncate(fd, FILE_SIZE) == -1) {
        perror("ftruncate");
        exit(1);
    }
    
    // 3. Отображаем файл в память (MAP_SHARED)
    void* ptr = mmap(NULL, FILE_SIZE, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
    if (ptr == MAP_FAILED) {
        perror("mmap");
        exit(1);
    }
    
    // 4. Работаем с памятью как с файлом
    const char* message = "Hello from tmpfs file!";
    strcpy((char*)ptr, message);
    printf("Записано в виртуальный файл: '%s'\n", message);

    // 5. Проверим, что данные действительно попали в файл
    printf("\nПроверка через чтение файла:\n");
    fflush(stdout);

    // Откроем тот же файл для чтения (как это сделал бы другой процесс)
    int fd_check = open(TMPFS_FILE, O_RDONLY);
    char buffer[256] = {0};
    read(fd_check, buffer, sizeof(buffer) - 1);
    printf("Содержимое '%s': '%s'\n", TMPFS_FILE, buffer);
    close(fd_check);

    // 6. Очистка
    munmap(ptr, FILE_SIZE);
    shm_unlink(TMPFS_FILE); // удаляем файл
	close(fd); // закрываем дескриптор
    return 0;
}
```

### 3.2. Маппинг в реальный файл на диске (file-backed)

Этот пример показывает, как изменения в памяти автоматически синхронизируются с обычным файлом на диске.

```c
// file_backed.c - Отображение реального файла на диске
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <fcntl.h>
#include <sys/mman.h>
#include <unistd.h>
#include <sys/stat.h>

#define REAL_FILE "test_data.txt"
#define FILE_SIZE 4096

int main() {
    // 1. Создаем/открываем реальный файл на диске
    int fd = open(REAL_FILE, O_CREAT | O_RDWR, 0666);
    if (fd == -1) {
        perror("open");
        exit(1);
    }
    
    // 2. Устанавливаем размер (делаем файл "дырчатым" - sparse file)
    if (ftruncate(fd, FILE_SIZE) == -1) {
        perror("ftruncate");
        exit(1);
    }
    
    // 3. Отображаем файл в память
    void* ptr = mmap(NULL, FILE_SIZE, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
    if (ptr == MAP_FAILED) {
        perror("mmap");
        exit(1);
    }
    
    // 4. Пишем в память (это автоматически изменит файл)
    const char* message = "Hello from memory-mapped file!";
    strcpy((char*)ptr, message);
    printf("Данные записаны в память. Файл будет обновлен ядром.\n");
    
    // 5. Явная синхронизация (опционально, но для демонстрации)
    printf("Принудительная синхронизация с диском...\n");
    if (msync(ptr, FILE_SIZE, MS_SYNC) == -1) {
        perror("msync");
    } else {
        printf("Синхронизация завершена.\n");
    }
    
    // 6. Проверяем содержимое реального файла
    printf("\nПроверка содержимого файла '%s':\n", REAL_FILE);
    fflush(stdout);
    
    FILE* f = fopen(REAL_FILE, "r");
    if (f) {
        char buffer[256] = {0};
        fread(buffer, 1, sizeof(buffer) - 1, f);
        printf("Файл содержит: '%s'\n", buffer);
        fclose(f);
    }
    
    // 7. Покажем, что файл может быть больше ОЗУ
    printf("\nДемонстрация работы с большим файлом:\n");
    off_t large_size = 1024 * 1024 * 10; // 10 МБ
    printf("Работа с файлом размером %ld байт (10 МБ)\n", (long)large_size);
    printf("При этом физической памяти может быть занято лишь несколько страниц.\n");
    
    // 8. Очистка
    munmap(ptr, FILE_SIZE);
    close(fd); // дескриптор больше не нужен
    // Не удаляем файл, чтобы его можно было проверить
    return 0;
}
```

### Ключевые отличия и особенности

| Характеристика | Виртуальный файл (`tmpfs`) | Реальный файл на диске |
|----------------|---------------------------|------------------------|
| **Расположение** | Только в ОЗУ (`/dev/shm`) | На постоянном носителе (HDD/SSD) |
| **Персистентность** | Исчезает при перезагрузке | Сохраняется после перезагрузки |
| **Размер** | Ограничен размером `tmpfs` (обычно 50% ОЗУ) | Ограничен свободным местом на диске |
| **Производительность** | Очень высокая (операции в ОЗУ) | Зависит от скорости диска и кэширования |
| **Demand paging** | Работает | Работает (файл может быть больше ОЗУ) |
| **Типичное применение** | Быстрый IPC, временные данные | Базы данных, работа с большими файлами |
