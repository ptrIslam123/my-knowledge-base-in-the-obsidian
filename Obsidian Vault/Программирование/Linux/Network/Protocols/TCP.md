**TCP** (Transmission Control Protocol — протокол управления передачей) — один из основных протокол передачи данных в интернета.
Механизм TCP предоставляет поток данных с предварительной установкой соединения, осуществляет повторный запрос данных в случае потери данных и устраняет дублирование при получении двух копий одного пакета, гарантируя тем самым (в отличие от [[UDP]]) целостность передаваемых данных и уведомление отправителя о результатах передачи.
# Установление TCP-соединения (Three-Way Handshake)

TCP — **полнодуплексный** и **надёжный** протокол. Прежде чем передавать данные, стороны должны:
1. **Синхронизировать ISN** (Initial Sequence Numbers) — начальные порядковые номера для каждого направления
2. **Подтвердить готовность** — убедиться, что обе стороны могут и отправлять, и принимать данные
3. **Согласовать параметры** — размер окна, опции (MSS, Window Scale, SACK и т.д.)

---

## Детальный разбор трёх шагов

### Шаг 1: SYN (Synchronize)

**Клиент → Сервер**

```
TCP Flags: SYN=1, ACK=0
tcp->seq  = ISN_client          (случайное 32-битное число)
tcp->ack_seq = 0                (не используется, т.к. ACK=0)
```

**Что происходит:**
- Клиент выбирает свой ISN (например, `1000`)
- Переходит в состояние **SYN-SENT**
- Отправляет сегмент с флагом SYN
- **Важно**: SYN занимает 1 байт в пространстве sequence numbers, хотя payload пустой

**Состояние сервера:** слушает порт (LISTEN), получает SYN.

---

### Шаг 2: SYN-ACK (Synchronize-Acknowledge)

**Сервер → Клиент**

```
TCP Flags: SYN=1, ACK=1
tcp->seq   = ISN_server         (свой случайный ISN, например 5000)
tcp->ack_seq = ISN_client + 1   (1001 = "жду байт 1001, твой SYN получил")
```

**Что происходит:**
- Сервер выбирает свой ISN (`5000`)
- Переходит в состояние **SYN-RECEIVED**
- Подтверждает получение клиентского SYN (`ack = 1001`)
- Отправляет свой SYN для синхронизации обратного направления
- **Выделяет ресурсы**: создаёт TCB (Transmission Control Block) — структуру в памяти для хранения состояния соединения (буферы, очереди, таймеры)

**Состояние клиента:** получает SYN-ACK, проверяет `ack_seq == ISN_client + 1`.

---

### Шаг 3: ACK (Acknowledge)

**Клиент → Сервер**

```
TCP Flags: SYN=0, ACK=1
tcp->seq   = ISN_client + 1     (1001 — первый байт реальных данных)
tcp->ack_seq = ISN_server + 1   (5001 = "жду байт 5001, твой SYN получил")
```

**Что происходит:**
- Клиент переходит в состояние **ESTABLISHED**
- Подтверждает получение серверного SYN (`ack = 5001`)
- Теперь может сразу отправлять **данные** в этом же пакете (если есть)
- Сервер, получив этот ACK, переходит в **ESTABLISHED**

---

## Полная схема с числами

```
Клиент (A)                                    Сервер (B)
ISN_A = 1000                                  ISN_B = 5000
[CLOSED]                                      [LISTEN]
   │                                               │
   │ ① SYN, SEQ=1000 ────────────────────────────>│
   │   [SYN-SENT]                                  │ [SYN-RECEIVED]
   │                                               │  (выделена память под TCB)
   │                                               │
   │ <────────────────────────── ② SYN/ACK,       │
   │      SEQ=5000, ACK=1001                       │
   │   [ESTABLISHED]                               │
   │                                               │
   │ ③ ACK, SEQ=1001, ACK=5001 ──────────────────>│
   │                                               │ [ESTABLISHED]
   │                                               │
   │  === Соединение установлено ===               │
   │                                               │
   │  DATA, SEQ=1001, ACK=5001, "Hello" ─────────> │
   │ <────────────────────  ACK=1006 (1001+5)      │
```

---

## Почему именно 3 шага, а не 2?

**Кратко**: так как tcp - дуплексный канал(система передачи данных, позволяющая обмениваться информацией в обоих направлениях одновременно), то и для установления с обоих сторон надежного соединения, требует не меньше 3 пакетов.

**Почему не 2-way handshake?**
- A отправляет SYN
- B отправляет SYN+ACK и считает соединение установленным
- **Проблема**: если SYN+ACK потерялся, A не знает, что B готов. B уже выделил ресурсы и ждёт данных, но A будет ретранслировать SYN или считать соединение неустановленным.
- **Результат**: полуоткрытое соединение (half-open), утечка ресурсов на сервере.

**3-way решает проблему:**
- Третий пакет (ACK) подтверждает, что клиент действительно получил параметры сервера и готов передавать данные.
- Сервер переходит в ESTABLISHED только после третьего шага, когда уверен в двусторонней связности.

---

## Безопасность: ISN и SYN Cookies

### Генерация ISN
ISN не должен быть предсказуемым (RFC 6528). Если атакующий угадает `ISN_B`, он может отправить фальшивый ACK и внедриться в соединение или вызвать разъединение.

**Алгоритм:**
```
ISN = M + F(localip, localport, remoteip, remoteport, secret)
```
Где `M` — монотонно увеличивающийся счётчик (каждые 4 мкс), `F` — криптографическая хеш-функция.

# Закрытие TCP-соединения (Four-Way Handshake)

TCP — полнодуплексный протокол, поэтому каждое направление закрывается **отдельно**. Для полного разрыва нужно закрыть оба потока: A→B и B→A.

## Детальный разбор четырёх шагов

### Шаг 1: FIN (Finish) — Active Close

**Инициатор (обычно клиент) → Противоположная сторона**

```
TCP Flags: FIN=1, ACK=1 (ACK обычно уже установлен)
tcp->seq   = snd_seq                (текущий указатель отправки)
tcp->ack_seq = rcv_seq              (подтверждение полученных данных)
```

**Что происходит:**
- Приложение вызывает `close()` или `shutdown(SHUT_WR)`
- Сторона больше не будет отправлять данные, но **готова принимать!**
- Отправляет FIN (занимает 1 байт в sequence space, как SYN)
- Переходит в состояние **FIN-WAIT-1**
- Сдвигает указатель: `snd_seq += 1` (за счёт FIN)

---

### Шаг 2: ACK (Acknowledgment)

**Противоположная сторона → Инициатор**

```
TCP Flags: ACK=1
tcp->ack_seq = snd_seq_инициатора + 1    (подтверждаем FIN)
tcp->seq   = rcv_seq                      (текущий указатель)
```

**Что происходит:**
- Получатель подтверждает получение FIN
- Уведомляет приложение (чтение из сокета возвращает 0 — EOF)
- Переходит в состояние **CLOSE-WAIT**
- **Важно**: получатель ещё может отправлять данные! (Half-Close)

Инициатор, получив ACK, переходит в **FIN-WAIT-2** и ждёт FIN от противоположной стороны.

---

### Шаг 3: FIN — Passive Close

**Противоположная сторона → Инициатор**

```
TCP Flags: FIN=1, ACK=1
tcp->seq   = snd_seq                (текущий указатель, включает FIN)
tcp->ack_seq = rcv_seq              (тот же ACK что в шаге 2)
```

**Что происходит:**
- Приложение на той стороне тоже вызывает `close()`
- Отправляется FIN для закрытия обратного направления
- Переходит в состояние **LAST-ACK**

---

### Шаг 4: ACK — Final Acknowledgment

**Инициатор → Противоположная сторона**

```
TCP Flags: ACK=1
tcp->ack_seq = snd_seq_противника + 1    (подтверждаем его FIN)
tcp->seq   = текущий                     (уже включал +1 за свой FIN)
```

**Что происходит:**
- Инициатор подтверждает получение FIN
- Переходит в состояние **TIME-WAIT**
- Противоположная сторона, получив ACK, переходит в **CLOSED** и освобождает ресурсы
- Инициатор ждёт 2×MSL (Maximum Segment Lifetime), затем переходит в **CLOSED**

---

## Полная схема с числами

```
Клиент (A)                                    Сервер (B)
[ESTABLISHED]                                 [ESTABLISHED]
snd=1500, rcv=3000                            snd=3000, rcv=1500

   │ ① FIN, SEQ=1500, ACK=3000 ─────────────────> │
   │   [FIN-WAIT-1]                                │ [CLOSE-WAIT]
   │   (snd_A = 1501)                              │ (rcv_B = 1501)
   │                                               │ (может ещё слать данные!)
   │                                               │
   │ <────────────────────── ② ACK, SEQ=3000,     │
   │                         ACK=1501              │
   │   [FIN-WAIT-2]                                │
   │                                               │
   │ <────────────────────── ③ FIN, SEQ=3200,     │  (B отправил ещё 200 байт
   │                         ACK=1501              │   с 3000 по 3199, затем FIN)
   │                                               │ [LAST-ACK]
   │                                               │
   │ ④ ACK, SEQ=1501, ACK=3201 ─────────────────> │
   │   [TIME-WAIT]                                 │ [CLOSED]
   │                                               │
   │   Ждёт 2×MSL (30-120 сек)                     │
   │   (на случай потери ACK ④)                   │
   │                                               │
   │   [CLOSED]                                   
```

---

## TIME-WAIT: зачем ждать 2×MSL?

**MSL** (Maximum Segment Lifetime) — максимальное время жизни сегмента в сети (обычно 30-60 сек, RFC 1122 рекомендует 2 мин).

### Две проблемы без TIME-WAIT:

**1. Поздний дубликат (Delayed Duplicate)**
- Пакет из старого соединения задержался в сети
- Новое соединение с теми же IP:port открывается
- Задержанный пакет приходит в новое соединение → **искажение данных**

**2. Потерянный последний ACK**
- Если ACK (шаг 4) потерян, сервер (LAST-ACK) не получит подтверждения
- Сервер будет ретранслировать свой FIN
- Клиент уже в CLOSED → приходит FIN, в ответ RST (сброс)
- Сервер получает RST вместо ACK → ошибка, а не graceful close

### Решение:
TIME-WAIT держит сокет 2×MSL, чтобы:
- Все старые пакеты гарантированно вымерли из сети
- Можно было переотправить ACK, если придёт повторный FIN

**SO_LINGER** опцией можно ускорить, но рискованно.

---

## Half-Close (Полузакрытое соединение)

TCP позволяет закрыть только **одно** направление:

```c
// Клиент больше не шлёт, но готов принимать
shutdown(sock, SHUT_WR);  // Отправляет FIN, переходит в FIN-WAIT-1

// Сервер получает EOF (read возвращает 0), но может писать
// Клиент читает до тех пор, пока сервер не закроет свой конец
```

**Пример использования:**
- Клиент отправляет запрос (POST), затем `shutdown(SHUT_WR)`
- Сервер читает запрос до EOF, обрабатывает, отправляет ответ
- Сервер закрывает соединение

В этом режиме клиент в FIN-WAIT-2 может **получать данные бесконечно долго**, пока сервер не отправит свой FIN.

---

## RST (Reset): немедленный сброс

Не всегда соединение закрывается gracefully:

```
Сценарии RST:
1. Порт закрыт (нет слушающего процесса)
2. Соединение разорвано приложением (SO_LINGER с нулевым таймаутом)
3. Пришёл пакет для несуществующего соединения
4. Проверка keepalive не пройдена
```

**Отличие от FIN:**
- RST **не ждёт** подтверждения
- Получатель RST немедленно разрывает соединение (нет TIME-WAIT)
- RST не занимает байт в sequence space (не требует ACK)

**[Главное правило: каждое направление закрывается отдельным FIN+ACK, и сторона, отправившая FIN первой, обязана подождать 2×MSL, защищая сеть от мусора.]**

# TCP SEQ & ACK

## 1. Базовые определения

| Поле           | Размер  | Назначение                                                                     |
| -------------- | ------- | ------------------------------------------------------------------------------ |
| `tcp->seq`     | 32 бита | Порядковый номер **первого байта** полезной нагрузки в потоке отправителя      |
| `tcp->ack_seq` | 32 бита | Номер **следующего ожидаемого байта** от партнёра (кумулятивное подтверждение) |

---

## 2. Инициализация (установление соединения)

```
Клиент (A)                          Сервер (B)
   │                                    │
   │  SYN, SEQ=ISN_A  ───────────────>  │  A: "мой поток начинается с ISN_A"
   │                                    │
   │  <────────────  SYN/ACK,           │  B: "мой поток с ISN_B, 
   │        SEQ=ISN_B, ACK=ISN_A+1      │      получил твой SYN, жду ISN_A+1"
   │                                    │
   │  ACK, SEQ=ISN_A+1,                 │  A: "мои данные с ISN_A+1,
   │     ACK=ISN_B+1  ───────────────>  │      получил твой SYN, жду ISN_B+1"
   │                                    │
   
Результат:
    У A: snd_seq = ISN_A + 1,  rcv_seq = ISN_B + 1 (что ждём от B)
    У B: snd_seq = ISN_B + 1,  rcv_seq = ISN_A + 1 (что ждём от A)
```

**Важно**: SYN и FIN занимают 1 байт в пространстве sequence numbers

---

## 3. Обмен данными (полнодуплексный)

### Отправка данных (сторона A → B)

```
Шаги отправителя (A):

1. Формирует пакет:
   tcp->seq = snd_seq                    ← текущий указатель в своём потоке
   payload  = n байт данных

2. Сохраняет копию в буфер ретрансляции (до получения ACK)

3. Сдвигает свой указатель:
   snd_seq += n                          ← готов к отправке следующих данных

4. Отправляет пакет
```

### Получение и подтверждение (сторона B)

```
Шаги получателя (B):

1. Принимает пакет от A:
   Проверяет: tcp->seq == rcv_seq ?      ← данные пришли по порядку?
   
   Если да:
   - записывает в буфер приложения
   - rcv_seq += n                         ← сдвигаем указатель ожидания
   
   Если нет (out-of-order):
   - буферизует, ждёт промежуточных сегментов
   - или использует SACK для частичного подтверждения

2. Формирует ответ (может быть с данными от B к A!):
   tcp->seq  = snd_seq_B                 ← свои данные (если есть)
   tcp->ack_seq = rcv_seq                 ← "жду от тебя байт rcv_seq"
   флаг ACK установлен всегда
```

---

## 4. Полная схема обмена

```
Время ──────────────────────────────────────────────────────────────>

A (ISN=100)                         B (ISN=500)
snd=101, rcv=501                    snd=501, rcv=101

   │  SEQ=101, len=10, data ───────> │
   │  (snd_A = 111)                  │  принял 101-110, rcv_B = 111
   │                                 │
   │  <──────────────  SEQ=501,      │
   │              ACK=111, len=5     │  (snd_B = 506)
   │                                 │  "получил твои байты до 111"
   │  принял 501-505, rcv_A = 506    │
   │                                 │
   │  SEQ=111, ACK=506, len=8 ─────> │
   │  (snd_A = 119)                  │  принял 111-118, rcv_B = 119
   │                                 │
   │  <──────────────  SEQ=506,      │
   │              ACK=119            │  "получил твои байты до 119"
   │                                 │
```

---

## Пример обмена пакетами сразу после tcp handshake

```text
Установление соединения:
    Клиент: ISN_client = 100
    Сервер: ISN_server = 500

После handshake:
    Клиент current = 101 (ISN + 1)
    Сервер current = 501 (ISN + 1)

Клиент отправляет n байт:
    tcp->seq = 101              ← текущий указатель
    current = 101 + n           ← сдвигаем у себя

Клиент ожидает ACK:
    tcp->ack_seq = 101 + n      ← "подтверди что получил до 101+n"
```

## Гарантия доставки (Reliability)

TCP использует **положительные подтверждения с повторной передачей** (Positive Acknowledgment with Retransmission - PAR).

### Механизм 1: Таймауты и ретрансмиссия (RTO)

```
Отправитель                                Получатель
   │                                          │
   │  SEQ=1000, len=100, data  ─────────────> │
   │  [запускает таймер RTO]                  │
   │                                          │
   │  [таймер истекает]                       │
   │  <-- ACK не получен!                     │
   │                                          │
   │  SEQ=1000, len=100, data  ─────────────> │  Ретрансмиссия
   │  [перезапуск таймера]                    │
   │                                          │
   │  <────────────────────────────  ACK=1100 │  Успех!
   │  [останавливает таймер]                  │
```

**RTO (Retransmission Timeout)**:
- Динамически рассчитывается на основе RTT (Round Trip Time)
- Формула (Jacobson/Karels): учитывает среднее RTT и дисперсию
- **Exponential backoff**: при повторных потерях RTO удваивается (1с, 2с, 4с, 8с...)

### Механизм 2: Fast Retransmit (Быстрая ретрансмиссия)

Проблема: при потере одного пакета ждать RTO (секунды) — медленно.

Решение: **3 дублирующих ACK** (Duplicate ACKs).

```
Отправитель послал:  SEQ=1000, 1100, 1200, 1300, 1400

Получатель:
   Получил 1000-1099 → ACK=1100
   Получил 1100-1199 → ACK=1200
   [Потерялся пакет 1200-1299]
   Получил 1300-1399 → ACK=1200 (дубликат! "жду 1200")
   Получил 1400-1499 → ACK=1200 (дубликат!)
   [Пришел еще один пакет] → ACK=1200 (дубликат!)

Отправитель видит 3 дублирующих ACK для 1200:
   → Считает пакет 1200 потерянным
   → Ретранслирует НЕМЕДЛЕННО, не дожидаясь RTO
   → Входит в режим Fast Recovery
```

### Механизм 3: Кумулятивные подтверждения

```c
// Логика получателя:
if (получен_сегмент_по_порядку) {
    rcv_seq += payload_len;
    отправить_ACK(rcv_seq);  // Подтверждаем все до rcv_seq
} else {
    отправить_повторный_ACK(rcv_seq);  // "Жду прежний байт"
}
```

**Важно**: Если получены сегменты 1000 и 1200, но потерян 1100:
- ACK будет `1100` (не 1300!)
- Сегмент 1200 буферизуется, но не подтверждается кумулятивно

# Гарантия порядка (Ordering)

TCP предоставляет приложению **поток байт в строгом порядке**, даже если сетевой уровень (IP) доставляет пакеты беспорядочно.

### Архитектура: Два буфера

```
Отправитель                                          Получатель
┌─────────────────┐                                 ┌──────────────────┐
│ Приложение      │                                 │ Сетевой интерфейс│
│ (write)         │                                 │ (IP-пакеты)      │
└────────┬────────┘                                 └────────┬─────────┘
         │                                                  │
         ▼                                                  ▼
┌─────────────────┐                                 ┌──────────────────┐
│ Send Buffer     │──────> Интернет (IP) ──────────>│ Receive Buffer   │
│ (ждет ACK)      │     (пакеты могут теряться      │ (вне порядка)    │
│                 │      и приходить вразброс)      │                  │
└─────────────────┘                                 └────────┬─────────┘
                                                             │
                                                             ▼
                                                    ┌──────────────────┐
                                                    │ Reordering Logic │
                                                    │ (сортировка)     │
                                                    └────────┬─────────┘
                                                             │
                                                             ▼
                                                    ┌──────────────────┐
                                                    │ Приложение       │
                                                    │ (read)           │
                                                    └──────────────────┘
```

### Алгоритм переупорядочивания

```
Получатель имеет:
   rcv_seq = 1000  (следующий ожидаемый байт)
   rcv_window = [1000, 2000]  (допустимый диапазон)

Сценарий 1: Пакет по порядку
   Приходит: SEQ=1000, len=100
   Действие: 
      - Отдать приложению (если буфер чтения свободен)
      - rcv_seq = 1100
      - Отправить ACK=1100

Сценарий 2: Пакет вне порядка (в окне)
   Приходит: SEQ=1200, len=100 (ждем 1100, а пришел 1200)
   Действие:
      - Сохранить в Receive Buffer (дыра между 1100 и 1200)
      - Отправить ACK=1100 (дублирующий!)
      - Ждать пакет 1100

Сценарий 3: Пришел недостающий пакет (заполнение дыры)
   Приходит: SEQ=1100, len=100
   Действие:
      - rcv_seq была 1000, но 1000-1099 уже приняты
      - Обнаруживаем: 1100-1199 пришли сейчас
      - Проверяем буфер: есть ли 1200-1299? ДА!
      - Объединяем: 1100-1299 непрерывны
      - rcv_seq = 1300
      - Отправить ACK=1300 (сразу за все!)
      - Передать приложению 1100-1299 (если возможно)
```

### SACK (Selective Acknowledgment) - RFC 2018

Стандартный TCP подтверждает только `rcv_seq` (кумулятивно). При потере пакета в середине:

```
Отправлено:  [1000] [1100] [1200] [1300] [1400]
Получено:    [1000] [1100]  X    [1300] [1400]

Без SACK:
   ACK=1100, 1100, 1100... (3 раза)
   Отправитель понимает, что потерялся 1100, но не знает про 1300, 1400
   Ретранслирует только 1100, ждет ACK

С SACK:
   ACK=1100 + SACK(1300-1400)
   Отправитель видит: "получил 1300-1400, но жду 1100-1200"
   Может ретранслировать только недостающий 1100
   Не пересылает 1300, 1400 повторно (экономия полосы)
```

**SACK блоки** в TCP-опциях:
- До 3 блоков непрерывных полученных данных
- Например: "Получил 1000-1099, пропустил 1100-1199, получил 1200-1499"

## 3. Управление потоком (Flow Control) — связь с гарантией

Чтобы гарантия доставки не привела к переполнению:

```
Получатель объявляет Window Size (в каждом ACK):
   ACK=1100, Window=1000  → "Я готов принимать байты 1100-2100"

Отправитель контролирует:
   - Неотправленные данные
   - Отправленные, но неподтвержденные (unacknowledged)
   - Доступное окно для отправки (min(congestion_window, receiver_window))

Если Window=0:
   Отправитель останавливается (Zero Window Probe каждые 30-60 сек)
```

## 4. Пример полного цикла с потерей и reordering

```
Время →

Отправитель (A)               Получатель (B)
                                          rcv_seq=1000
1. Отправляет SEQ=1000, len=100 ───────>  [буфер: пусто]
   [Таймер RTO старт]                     

2. Отправляет SEQ=1100, len=100 ───────>X  [ПОТЕРЯН!]
   [Таймер RTO старт]

3. Отправляет SEQ=1200, len=100 ───────>  [буфер: [1200-1299]]
                                           (вне порядка, ждет 1100)
                                          Отправляет ACK=1100

4. Получает ACK=1100                      (dup ACK #1)

5. Отправляет SEQ=1300, len=100 ───────>  [буфер: [1200-1299],[1300-1399]]
                                          Отправляет ACK=1100 (dup #2)

6. Получает ACK=1100                      (dup ACK #3!)
                                          → Fast Retransmit!
                                          → Ретранслирует SEQ=1100

7. Отправляет SEQ=1100, len=100 ───────>  [получил 1100!]
                                          Проверяет буфер:
                                          Есть 1200? ДА
                                          Есть 1300? ДА
                                          rcv_seq = 1400
                                          Отправляет ACK=1400
                                          Передает приложению 1100-1399

8. Получает ACK=1400                      [останавливает все таймеры]
                                          Сдвигает окно отправки
```
