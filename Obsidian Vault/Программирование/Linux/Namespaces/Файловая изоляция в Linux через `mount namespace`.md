
`mount namespace` — это механизм ядра Linux, который позволяет разным процессам (или группам процессов) **видеть разные иерархии смонтированных файловых систем**. Вместо одного глобального "взгляда" на диски, каждый `mount namespace` получает свою **личную копию списка точек монтирования**. Это основа файловой изоляции в контейнерах (Docker, LXC) и sandbox-сервисах (systemd).

**Ключевое:** изолируется не содержимое файлов, а *точки монтирования* и *структура дерева ФС*.

---

## Как это работает под капотом (пошагово)

### Шаг 1: В системе по умолчанию
- Существует **главный (init) `mount namespace`**.
- Все процессы изначально его наследуют.
- Ядро поддерживает для каждого namespace **собственный список точек монтирования** (например: `/`, `/home`, `/proc`, `/sys`, `/tmp` и другие директории, куда смонтированы файловые системы).

### Шаг 2: Создание нового `mount namespace`
- Вызов: `unshare(CLONE_NEWNS)` или `clone(... | CLONE_NEWNS)`.
- Ядро копирует таблицу монтирований из **родительского mount namespace** в новый. Новый процесс наследует тот namespace, в котором он создан.
- Наследник видит **точно те же самые** точки монтирования (на момент создания). **Важно:** При обычном `fork()` дочерний процесс наследует mount namespace родителя. Чтобы создать **новый** namespace, нужно использовать `unshare()` или `clone()` с флагом `CLONE_NEWNS`.

### Шаг 3: Изоляция
- Дальнейшие вызовы `mount()` и `umount()` внутри нового namespace **меняют только его собственную копию таблицу точке монтирвоаний**.
- Родительский namespace (например, хост) **не видит** этих изменений(так как каждый работает со своей копией таблицы точке мантирования).
- При завершении всех процессов внутри namespace его таблица уничтожается.

> **Важно:** Это **не** chroot, не виртуализация и не эмуляция. Это реальное отделение таблицы монтирований.

## Главный принцип изоляции
##### Два совершенно разных смысла `mount`

| Аспект              | физическое устройство                                 | namespaces                                                 |
| ------------------- | ----------------------------------------------------- | ---------------------------------------------------------- |
| **Что монтируем?**  | Реальное устройство (диск, USB, раздел)               | Виртуальную ФС (`tmpfs`) или другую директорию (`--bind`)  |
| **Зачем?**          | Чтобы получить доступ к данным на физическом носителе | Чтобы **скрыть** или **подменить** существующую директорию |
| **Где это видно?**  | Всей системе (глобально)                              | Только внутри конкретного `mount namespace`                |
| **Типичный пример** | `mount /dev/sdb1 /mnt/usb`                            | `mount --bind /пусто /home` (чтобы скрыть `/home`)         |

---

##  **классический сценарий монтирования**

> 1. Подключаем USB-флешку → появляется устройство `/dev/sdb1`
> 2. Монтируем его в директорию: `mount /dev/sdb1 /mnt/usb`
> 3. Создаём файловую систему (если нужно): `mkfs.ext4 /dev/sdb1`
> 4. Теперь в `/mnt/usb` можно создавать файлы и директории

**Это 100% правильное понимание `mount`.** Именно так монтирование работает в Linux с 1990-х годов.

## 🔄 А что тогда мы обсуждали про namespaces?

Есть **второй, более тонкое применение** `mount`, которое появилось позже (в 2000-х с появлением namespaces):

### 1. Монтирование `tmpfs` (виртуальная ФС в ОЗУ)

```bash
mount -t tmpfs tmpfs /home
```
- Нет никакого USB, диска, раздела.
- Данные лежат **в оперативной памяти**.
- При отмонтировании или выключении — всё исчезает.
- Используется для создания "чистого" `/tmp` или скрытия директорий.

### 2. `bind mount` — привязка одной директории к другой

```bash
mount --bind /пустая/папка /home
```
- **Нет никакого нового устройства.**
- Мы просто говорим ядру: "Теперь при обращении к `/home` показывай содержимое `/пустая/папка`".
- Оригинальный `/home` при этом **остаётся нетронутым**, просто "заклеенным".

---

1. **Зачем это нужно?** Чтобы скрыть от контейнера реальные папки хоста, не отключая и не трогая их физически.

2. **Почему так сделано?** Потому что в Linux фраза "смонтировать" означает не только "подключить диск", но и вообще **"установить соответствие между путём и тем, что показывать при обращении к этому пути"**.

---

### Ошибочное представление ❌
> "Чтобы скрыть `/home` от контейнера, нужно выполнить `umount /home` внутри его namespace."

**Почему это плохо:**
- Критические ФС (`/proc`, `/sys`, `/dev`) **нельзя отмонтировать** у работающего процесса (ошибка `busy`).
- Это деструктивно: если внутри namespace запущены процессы, они потеряют доступ к важным точкам.
- Негибко: вы не сможете "вернуть назад" скрытую директорию без пересоздания namespace.

### Правильный подход ✅
> **Монтирование ПОВЕРХ (overmounting)** – создание "белого шума" поверх защищаемой директории.

**Механизм:**
```bash
# Внутри нового mount namespace:
mount --bind /пусто/или/что-то /защищаемая/директория
# или
mount -t tmpfs tmpfs /защищаемая/директория
```

**Что происходит:**
1. В таблице монтирований namespace появляется **новая запись** с путём `/защищаемая/директория`.
2. Старое содержимое этой директории **становится недоступным** (скрытым) внутри этого namespace.
3. На хосте (в другом namespace) эта директория остаётся **нетронутой**.
4. Можно легко "вернуть назад", сделав `umount` этой верхней точки.

**Преимущества:**
- Работает с любыми ФС (`/proc`, `/sys`, `/dev`, `tmpfs`, `ext4`).
- Не требует размонтирования системных точек.
- Полностью обратимо.

## Визуальная модель (аналогия)

Представьте **общую карту города** (глобальная таблица монтирований):

- **Обычный процесс** смотрит на оригинальную карту.
- **Новый `mount namespace`** = делается **копия** этой карты на кальке.
- **Изоляция** = поверх кальки наклеиваются **белые стикеры** с надписью "проезда нет" на те улицы, которые нужно скрыть.
- **Хост** (оригинал карты) **не замечает** этих наклеек.
- Когда процесс завершается, **калька со стикерами выбрасывается**.

**Нет никакого "отрезания" улиц от оригинала!** Только заклеивание на личной копии.

## Сравнение с другими механизмами (очень важно не путать!)

| Механизм | Что делает? | Связь с `mount namespace` |
|----------|-------------|--------------------------|
| **`chroot()`** | Меняет корневой каталог `/` для процесса. | **Не изолирует** точки монтирования. Можно внутри `chroot` выполнить `mount --bind` и увидеть реальную ФС хоста. |
| **`pivot_root()`** | Безопасно заменяет корневую ФС (используется в Docker). | **Тоже не изолирует** таблицу монтирований, только меняет точку `/`. |
| **`mount namespace`** | Изолирует **саму таблицу** монтирований. | Позволяет каждому пространству иметь свой набор `mount`/`umount`. |

**Идеальная связка для контейнера:**
1. Создать новый `mount namespace` (чтобы не видеть изменения хоста).
2. Выполнить `pivot_root` в папку контейнера (чтобы сменить корень).
3. Внутри нового корня выполнить свои `mount` (`/proc`, `/sys`, `/dev`).

## Практический пример для закрепления (можно выполнить)

```bash
# Открываем терминал хоста
mkdir /tmp/test_real /tmp/test_hide

# Хост: видим реальные файлы
ls /tmp/test_real

# Создаём новый mount namespace и запускаем bash
sudo unshare --mount bash

# Теперь мы внутри нового namespace
# Скрываем /tmp/test_real, монтируя поверх временную ФС
mount -t tmpfs tmpfs /tmp/test_real

# Проверяем: внутри namespace /tmp/test_real пуст
ls /tmp/test_real

# Выходим из namespace
exit

# На хосте: /tmp/test_real снова виден и не изменился
ls /tmp/test_real
```

**Результат:** временная "ширма" внутри namespace не повлияла на хост.
