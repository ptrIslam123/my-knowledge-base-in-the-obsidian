Связанные темы: [[Файловая изоляция в Linux через `mount namespace`]]
Если `mount namespace` даёт процессу **свою личную копию таблицы монтирований**, то `network namespace` даёт процессу **свой личный сетевой стек**.

**Что входит в понятие "сетевой стек":**
- Сетевые интерфейсы (`eth0`, `wlan0`, `lo`)
- IP-адреса и маски
- Таблицы маршрутизации (`route -n`)
- Правила фаервола (`iptables`, `nftables`)
- Сетевые сокеты (TCP, UDP, UNIX)
- Сетевые очереди (netfilter)
- `/proc/net` и `/sys/class/net`

**Ключевое:** процесс в своём network namespace видит **только свои** интерфейсы, маршруты и правила. Он **не видит** интерфейсы хоста и других namespaces.

---

## Как это работает

### Шаг 1: В системе по умолчанию
- Существует **главный (init) network namespace**.
- Все процессы изначально его наследуют.
- В нём видны все физические интерфейсы хоста (`eth0`, `lo` и т.д.).

### Шаг 2: Создание нового network namespace
- Вызов: `unshare(CLONE_NEWNET)` или `ip netns add <name>`.
- Ядро создаёт **абсолютно новый, пустой сетевой стек** (НЕ КОПИЮ КАК С [[Файловая изоляция в Linux через `mount namespace`]] — это важно).
- В новом namespace есть **только один интерфейс** — `lo` (loopback), и он по умолчанию **выключен** (DOWN).

### Шаг 3: Изоляция
- Процессы в разных network namespaces **не видят** сетевые интерфейсы друг друга.
- Можно слушать один и тот же порт (например, 80) в разных namespaces — **конфликта не будет**.
- Соединение между namespaces нужно **организовывать явно** (через `veth`-пары).

> **Важное отличие от mount namespace:** при создании mount namespace мы делаем **копию** таблицы. При создании network namespace мы делаем **чистый лист** — пустой стек.

---

## Аналогия для понимания

Представьте **коммутатор в офисе** (главный network namespace):

- Все компьютеры подключены к этому коммутатору, видят друг друга.
- **Новый network namespace** = вы ставите **новый, пустой коммутатор в соседней комнате**.
- На нём нет никаких подключений (только петля для самого себя — `lo`).
- Чтобы соединить коммутаторы между собой, нужно протянуть **кабель** (`veth`-пару) и настроить IP-адреса на обоих концах.

**Коммутаторы изолированы — трафик не ходит между ними без явного кабеля.**

## Практическая работа с network namespaces (инструменты)

В Linux есть два способа:

| Способ | Команды | Назначение |
|--------|---------|------------|
| **Старый (unshare)** | `unshare -n bash` | Быстрое тестирование, разовые эксперименты |
| **Удобный (ip netns)** | `ip netns add`, `ip netns exec` | Постоянное управление, контейнеры |

### 1. Создание и просмотр

```bash
# Создать новый network namespace по имени
sudo ip netns add red
sudo ip netns add blue

# Посмотреть все namespaces
ip netns list
# red
# blue

# Запустить команду внутри namespace
sudo ip netns exec red bash
# Теперь вы внутри "red"
ip link show
# 1: lo: <LOOPBACK> ... DOWN (только loopback, выключен)
exit
```

### 2. Соединение двух namespaces (veth-пара)

`veth` — это **виртуальный Ethernet-кабель** с двумя концами.

```bash
# Создаём veth-пару: красный конец и синий конец
sudo ip link add veth-red type veth peer name veth-blue

# Помещаем каждый конец в свой namespace
sudo ip link set veth-red netns red
sudo ip link set veth-blue netns blue

# Внутри каждого namespace настраиваем IP-адреса
sudo ip netns exec red ip addr add 10.0.0.1/24 dev veth-red
sudo ip netns exec red ip link set veth-red up
sudo ip netns exec red ip link set lo up

sudo ip netns exec blue ip addr add 10.0.0.2/24 dev veth-blue
sudo ip netns exec blue ip link set veth-blue up
sudo ip netns exec blue ip link set lo up

# Проверяем связь
sudo ip netns exec red ping 10.0.0.2
# PING 10.0.0.2 (10.0.0.2) ... работает!
```

**Визуализация:**
```
┌─────────────┐      veth-пара      ┌─────────────┐
│   red       │  ┌─────────────┐   │   blue      │
│  10.0.0.1   │──│ veth-red    │───│ veth-blue   │──│ 10.0.0.2   │
│             │  └─────────────┘   │             │
└─────────────┘                    └─────────────┘
```

## Мост и NAT

### Проблема, которую мы решаем

У нас есть:
- **Namespace "red"** с интерфейсом `veth-red` и IP `192.168.100.2/24`
- **Хост** с основным интерфейсом `eth0` и IP `192.168.1.100` (или любым другим, который смотрит в интернет)

**Проблема:** namespace "red" не имеет выхода в интернет. Он видит только свой интерфейс `veth-red` и loopback `lo`.

**Вопрос:** Как дать namespace "red" возможность пинговать `8.8.8.8`?

**Ответ:** Есть два основных способа — **NAT** и **мост**.

---

### Общая схема для обоих способов

В обоих случаях мы используем `veth`-пару (виртуальный кабель):

```
┌────────────────────────────────────────────────────────────┐
│                           Хост                             │
│  ┌─────────────────┐                    ┌───────────────┐  │
│  │   namespace red │                    │   host stack  │  │
│  │                 │                    │               │  │
│  │  veth-red       │                    │  veth-host    │  │
│  │  192.168.100.2  │◄─── veth-пара ────►│ 192.168.100.1 │  │
│  │                 │                    │               │  │
│  └─────────────────┘                    └───────┬───────┘  │
│                                                  │         │
│                                                  │ eth0    │
│                                                  │ 192.168.1.100
└──────────────────────────────────────────────────┼─────────┘
                                                   │
                                                Интернет
```

**Что мы уже сделали:**
1. Создали `veth`-пару
2. Поместили один конец (`veth-red`) в namespace red
3. Настроили IP-адреса на обоих концах
4. Подняли интерфейсы

Теперь red и хост **видят друг друга** (могут пинговать `192.168.100.1` и `192.168.100.2`). Но в интернет red ещё не выходит.

---
### СПОСОБ 1: Мост (Bridge)

## Идея моста

**Мост — это виртуальный коммутатор (switch).** Все интерфейсы, подключённые к мосту, оказываются в одной сети и могут общаться напрямую.

В отличие от NAT, здесь:
- **Нет подмены IP-адресов**
- **Хост и namespace находятся в одной подсети**
- Все участники **видят реальные IP друг друга**

## Схема с мостом

```
                         Интернет
                            │
                      ┌─────┴─────┐
                      │ маршрутизатор │
                      │ 192.168.1.1   │
                      └─────┬─────┘
                            │
                      ┌─────┴─────┐
                      │   Хост    │
                      │           │
                      │   br0     │◄─── мост (виртуальный коммутатор)
                      │ 192.168.1.50
                      └─────┬─────┘
                            │
            ┌───────────────┼───────────────┐
            │               │               │
       ┌────┴────┐     ┌────┴────┐     ┌────┴────┐
       │ veth-host│     │ veth-host│     │  eth0   │
       │ (red)   │     │ (blue)  │     │  (основной)
       └────┬────┘     └────┬────┘     └────┬────┘
            │               │               │
       ┌────┴────┐     ┌────┴────┐          │
       │  red    │     │  blue   │          │
       │192.168.1.51│    │192.168.1.52│      │
       └─────────┘     └─────────┘          │
                                            │
                                    физическая сеть
```

## Как проходит пакет через мост

```
1. red (192.168.1.51) пингует 8.8.8.8
   Источник: 192.168.1.51 → Назначение: 8.8.8.8

2. Пакет идёт через veth-red → veth-host-red

3. veth-host-red подключён к мосту br0
   Мост работает как коммутатор (L2)

4. Мост смотрит на IP-адрес назначения:
   - 8.8.8.8 не в локальной сети → нужно отправить на маршрутизатор
   - Маршрутизатор имеет MAC-адрес, известный мосту через интерфейс eth0

5. Пакет выходит через eth0 в физическую сеть
   Источник: 192.168.1.51 → Назначение: 8.8.8.8 (IP не менялся!)

6. Маршрутизатор (192.168.1.1) получает пакет и отправляет в интернет

7. Ответ идёт обратно:
   8.8.8.8 → 192.168.1.51

8. Маршрутизатор отправляет пакет в сеть 192.168.1.0/24

9. Мост br0 получает пакет на eth0, смотрит MAC-адрес назначения
   и отправляет на veth-host-red

10. Пакет доходит до red
```

## Плюсы и минусы моста

| Плюсы | Минусы |
|-------|--------|
| ✅ Полная прозрачность (видно реальные IP) | ❌ Сложнее настройка (нужно настраивать внешний маршрутизатор) |
| ✅ Нет накладных расходов на NAT | ❌ Требуется выделенный IP для каждого namespace |
| ✅ Легко организовать связь между namespaces | ❌ Может конфликтовать с DHCP |
| ✅ Поддерживает broadcast/multicast | ❌ При подключении eth0 к мосту хост теряет прямой доступ к сети |

### СПОСОБ 2: NAT (Network Address Translation)

#### Идея NAT

**Хост выступает в роли маршрутизатора,** который подменяет IP-адрес отправителя.

Когда пакет из red идёт в интернет:
1. Хост получает пакет от red (с источником `192.168.100.2`)
2. Хост **подменяет** исходный IP на свой собственный (`192.168.1.100`)
3. В интернет уходит пакет, как будто его отправил сам хост
4. Когда приходит ответ, хост делает обратную подмену и передаёт пакет в red
## Как проходит пакет (трассировка)

```
1. red: ping 8.8.8.8
   Источник: 192.168.100.2 → Назначение: 8.8.8.8

2. Пакет идёт через veth-пару на хост (veth-host)

3. Хост получает пакет на veth-host (IP 192.168.100.1)
   Ядро видит: пакет не для меня (назначение 8.8.8.8)
   IP-форвардинг включён → пересылаем дальше

4. Хост смотрит маршрут до 8.8.8.8 → через eth0

5. Срабатывает правило MASQUERADE (POSTROUTING)
   Исходный IP подменяется: 192.168.100.2 → 192.168.1.100

6. В интернет уходит пакет:
   Источник: 192.168.1.100 → Назначение: 8.8.8.8

7. Сервер 8.8.8.8 отвечает:
   Источник: 8.8.8.8 → Назначение: 192.168.1.100

8. Хост получает ответ, смотрит таблицу connection tracking
   (ядро запомнило, что этот ответ относится к пакету из red)

9. Обратная подмена: 192.168.1.100 → 192.168.100.2

10. Пакет уходит через veth-host в red
```

## Плюсы и минусы NAT

| Плюсы | Минусы |
|-------|--------|
| ✅ Простая настройка (одна команда) | ❌ Проблемы с входящими соединениями (нужен DNAT) |
| ✅ Не требует дополнительных IP-адресов | ❌ Нарушает сквозную IP-связность |
| ✅ Работает "из коробки" с любым провайдером | ❌ Некоторые протоколы (FTP, SIP) требуют особой обработки |
| ✅ Безопасность (внутренние IP не видны извне) | ❌ Снижение производительности (пересчёт контрольных сумм) |

---

# Сравнение NAT и моста (шпаргалка)

| Характеристика | NAT | Мост |
|----------------|-----|------|
| **Изменяет IP пакета?** | Да (source NAT) | Нет |
| **Нужен ли отдельный IP для namespace?** | Нет (приватные IP) | Да (IP из внешней сети) |
| **Виден ли namespace извне?** | Нет (без DNAT) | Да (как обычный хост) |
| **Простота настройки** | Высокая | Средняя |
| **Производительность** | Немного ниже (пересчёт контрольных сумм) | Максимальная |
| **Где используется** | Docker (стандартно), домашние сети | Контейнеры в режиме host network, виртуальные машины, профессиональные настройки |

## Docker: как это работает на практике

Docker использует **оба подхода** в зависимости от режима:

| Режим Docker | Технология | Описание |
|--------------|------------|----------|
| **bridge (по умолчанию)** | NAT + мост | Создаётся мост `docker0` (172.17.0.0/16), контейнеры получают IP из этой сети, проброс портов через NAT |
| **host** | Нет изоляции | Контейнер использует network namespace хоста |
| **none** | Только loopback | Контейнер изолирован полностью |
| **macvlan** | Мост + физический интерфейс | Контейнер получает IP из внешней сети |

**Стандартная схема Docker:**
```bash
# Docker создаёт:
# 1. Мост docker0 (172.17.0.1)
# 2. Для каждого контейнера: veth-пару (один конец в контейнере с IP 172.17.0.x)
# 3. Правило MASQUERADE для выхода в интернет
# 4. При запуске с -p 8080:80 — добавляет DNAT
```

## Где это используется в реальности

| Технология | Как использует network namespaces |
|------------|-----------------------------------|
| **Docker** | Каждому контейнеру — свой network namespace (если не указан `--net=host`) |
| **Kubernetes** | Каждый pod получает свой network namespace (общий для всех контейнеров pod) |
| **LXC/LXD** | Каждому контейнеру — свой сетевой стек |
| **systemd** | `PrivateNetwork=yes` создаёт новый network namespace только с `lo` |
| **VPN-клиенты** | Некоторые изолируют трафик в отдельный namespace, чтобы не смешивать с хостом |
| **Тестирование сети** | Можно эмулировать несколько изолированных устройств на одном хосте |
