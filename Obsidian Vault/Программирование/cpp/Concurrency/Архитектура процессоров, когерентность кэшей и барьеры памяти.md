
## Часть 1: Проблема — почему вообще нужна вся эта сложность?

### 1.1. Базовая проблема
- Процессоры работают на частоте 3-4 ГГц (1 операция за ~0.3 нс)
- DRAM память имеет задержку 100-300 нс (в 300-1000 раз медленнее!)
- **Решение:** Кэш-память (SRAM) — 1-4 нс для L1, 10-30 нс для L3

### 1.2. Иерархия памяти
```
Регистры (0-1 цикл) → L1 кэш (2-4 цикла, 32-64 KB) → L2 кэш (10-15 циклов, 256KB-1MB) → L3 кэш (30-50 циклов, 2-32 MB) → DRAM (300-600 циклов)
```

### 1.3. Проблема многопоточности
- У каждого ядра свой L1/L2 кэш (приватные)
- Данные могут быть одновременно в кэшах разных ядер
- Без синхронизации: ядро 0 пишет X=1, ядро 1 читает X=0 (старое значение)

## Часть 2: Кэш-память и её организация

### 2.1. Структура кэша
- **Кэш-линия:** 64 байта (атомарная единица когерентности)
- **Теги:** идентифицируют, какие адреса памяти хранятся
- **Состояния:** описывают, как ядро может работать с линией

### 2.2. Распределение кэшей
| Уровень | Размер | Приватность | Задержка | Назначение |
|---------|--------|-------------|----------|------------|
| L1 Data | 32KB | Приватный | 2-4 цикла | Самые горячие данные |
| L1 Inst | 32KB | Приватный | 2-4 цикла | Инструкции |
| L2 | 256KB-1MB | Приватный (Intel) / Shared (AMD) | 10-15 циклов | Буфер между L1 и L3 |
| L3 | 2-32MB | Shared (все ядра) | 30-50 циклов | Последняя надежда перед DRAM |

### 2.3. Ложное разделение (false sharing)
```cpp
struct Data {
    int a;  // ядро 0 пишет
    int b;  // ядро 1 читает
}; // оба поля в одной кэш-линии → конфликт!
```

## Часть 3: Протокол когерентности кэшей (MESI)

### 3.1. Зачем нужен
**Обеспечивает:** все ядра в итоге видят одинаковые значения для одного адреса
**Не обеспечивает:** порядок изменений разных адресов

### 3.2. Состояния MESI

| Состояние | Значение | У меня | В памяти | Другие ядра |
|-----------|----------|--------|----------|--------------|
| **M**odified | Я изменил | Актуально | Устарело | Нет копии |
| **E**xclusive | Только у меня | Актуально | Актуально | Нет копии |
| **S**hared | Только чтение | Актуально | Актуально | Могут быть |
| **I**nvalid | Устарело | Недейств. | Любое | Не важно |

### 3.3. Переходы между состояниями

```
   Чтение          Запись         Инвалидация
      ↓               ↓              ↓
   ┌─────┐          ┌─────┐        ┌─────┐
   │ I   │──запись→ │ M   │←запись─│ E   │
   └─────┘          └─────┘        └─────┘
      ↑                ↑              ↑
      └────чтение──────┘              │
      └──────────────S───────────────┘
```

### 3.4. Пример работы
```cpp
// Исходно: X=100 в памяти

// 1. Ядро 0: читает X
//    → загружает из памяти, состояние EXCLUSIVE

// 2. Ядро 1: читает X  
//    → snoop-запрос, ядро 0: SHARED, ядро 1: SHARED

// 3. Ядро 0: пишет X=200
//    → отправляет RFO (Read For Ownership)
//    → ядро 1: INVALID, ядро 0: MODIFIED

// 4. Ядро 1: читает X
//    → кэш-промах → запрос на шину
//    → ядро 0: отдаёт 200, оба в SHARED
```

## Часть 4: Очереди ядра (оптимизации, ломающие когерентность)

### 4.1. Store Buffer (исходящая очередь)

**Проблема:** Запись в кэш требует RFO запроса (сотни циклов)
**Решение:** Буфер для записей (8-32 элемента)

**Как работает:**
```cpp
x = 1;  // 1. Значение кладётся в Store Buffer (1-2 цикла)
        // 2. Инструкция считается завершённой
        // 3. В фоне: запись в L1 кэш (100+ циклов)
```

**Что ломает:** 
- Другие ядра НЕ видят запись, пока она в буфере
- Записи могут вытолкнуться в кэш в другом порядке

**Размер:** 8-32 записи (очень маленький)
**Время:** 1-2 цикла на помещение

### 4.2. Event Queue (Invalidation Queue / Snoop Queue)

**Проблема:** Если обрабатывать каждый snoop-запрос мгновенно, ядро постоянно прерывается
**Решение:** Очередь входящих сообщений

**Как работает:**
```
Другие ядра → [INVALIDATE addr1] → Event Queue → (ждёт) → Обновление L1
              [SHARE addr2]    
              [READ addr1]      
```

**Что ломает:**
- Пока сообщение в очереди, кэш считается актуальным (но это не так!)
- Ядро может прочитать устаревшие данные

**Когда обрабатывается:**
- На границах базовых блоков
- При инструкциях барьера (особенно acquire)
- Примерно каждые N циклов

### 4.3. Load Buffer (Line Fill Buffer)

**Проблема:** Чтение при кэш-промахе тоже долгое
**Решение:** Буфер ожидающих загрузок (non-blocking cache)

**Как работает:**
```
ldr x3, [addr]  // адреса нет в кэше
                 → помещается в Load Buffer
                 → процессор продолжает работу
                 → когда данные придут, записываются в регистр
```

## Часть 5: Проблемы, возникающие из-за очередей

### 5.1. StoreStore reordering
```cpp
// Ядро 0
x = 1;  // в буфер
y = 1;  // в буфер (может обогнать x!)

// Проблема: другие ядра могут увидеть y=1 раньше x=1
```

### 5.2. StoreLoad reordering (самый опасный)
```cpp
// Ядро 0            // Ядро 1
x = 1;               y = 1;
r1 = y;              r2 = x;

// Результат r1=0, r2=0 возможен!
// Почему:
// 1. Записи в Store Buffer (ещё не видны)
// 2. Чтения из L1 (старые значения)
```

### 5.3. LoadLoad reordering (на слабой памяти)
```cpp
// Ядро 0            // Ядро 1
x = 1;               while (flag == 0);
flag = 1;            r1 = x;
                     r2 = y;  // может прочитаться ДО r1!
```

### 5.4. Почему когерентности недостаточно?

| Ошибка | Причина |
|--------|---------|
| "Когерентность гарантирует порядок" | НЕТ — только конечную видимость |
| "Store buffer только для производительности" | ДА, но именно он ломает порядок |
| "Event queue можно игнорировать" | НЕТ — без барьеров данные устаревают |

## Часть 6: Барьеры памяти (инструкции)

### 6.1. Что такое барьер
**Определение:** Инструкция процессора, запрещающая переупорядочивание операций через неё

**Реализация:** через принудительную работу с очередями

### 6.2. Реальные инструкции (ARM)

| Инструкция | Store Buffer | Event Queue | Запрещает |
|-----------|--------------|-------------|-----------|
| `DMB ISHST` | Опустошить | Не трогает | store-store, load-store |
| `DMB ISHLD` | Не трогает | Обработать | load-load, load-store |
| `DMB ISH` | Опустошить | Обработать | все типы |
| `DSB ISH` | Опустошить + ждать | Обработать + ждать | полная синхронизация |

### 6.3. Реальные инструкции (x86)

| Инструкция | Что делает | Когда нужна |
|-----------|-----------|-------------|
| `MFENCE` | Полный барьер (store+load) | seq_cst, атомарные RMW |
| `SFENCE` | Только для store | Release semantics (редко) |
| `LFENCE` | Только для load | Acquire semantics (почти никогда) |

**Важно:** x86 аппаратно запрещает почти все переупорядочивания, кроме StoreLoad

### 6.4. Типы барьеров (абстракции)

| Тип | Запрещает | Реализация ARM | Реализация x86 |
|-----|-----------|---------------|----------------|
| `#LoadLoad` | load после load | `DMB ISHLD` | (аппаратно) |
| `#StoreStore` | store после store | `DMB ISHST` | `SFENCE` |
| `#LoadStore` | load после store | `DMB ISHLD` + `DMB ISHST` | (аппаратно) |
| `#StoreLoad` | load после store | `DMB ISH` | `MFENCE` |

## Часть 7: std::memory_order в C++

### 7.1. Трансляция в инструкции

| memory_order | Операция | x86 | ARM (Linaro) |
|--------------|----------|-----|--------------|
| `relaxed` | load/store | `MOV` | `LDR`/`STR` |
| `acquire` | load | `MOV` + compiler barrier | `LDAR` или `LDR` + `DMB ISHLD` |
| `release` | store | `MOV` + compiler barrier | `STLR` или `DMB ISHST` + `STR` |
| `acq_rel` | RMW | `LOCK XCHG` | `LDAR` + `STLR` |
| `seq_cst` | load | `MOV` (x86 гарантирует) | `LDAR` |
| `seq_cst` | store | `XCHG` или `MOV` + `MFENCE` | `DMB ISH` + `STR` |

### 7.2. Что запрещает каждый memory_order

```cpp
// relaxed: ничего не запрещает
x.store(1, relaxed);  // может быть переставлено куда угодно

// acquire: load не может быть переставлен ВНИЗ
int r = x.load(acquire);
y = 1;  // НЕ может оказаться перед load!
z = 2;  // НЕ может оказаться перед load!

// release: store не может быть переставлен ВВЕРХ  
x = 1;
y.store(2, release);  // x=1 НЕ может оказаться после y
z = 3;                // может быть после

// acq_rel: и то, и другое (для RMW)

// seq_cst: глобальный порядок (все видят операции в одном порядке)
```

### 7.3. Пример правильного использования

```cpp
// Producer-consumer без блокировок
// Поток 1 (Producer)
data = 42;
flag.store(true, std::memory_order_release);  // data виден до flag

// Поток 2 (Consumer)
while (!flag.load(std::memory_order_acquire));  // flag виден до data
int result = data;  // гарантированно видит 42
```

## Часть 8: Полный цикл работы (собираем всё вместе)

### 8.1. Пример с эффектом StoreLoad

```cpp
// Исходно: x=0, y=0 (обе линии в L1 ядра 0, состояние E)

// t=0: Ядро 0: x=1
//   → Store Buffer: [x=1, pending]
//   → Ядро продолжает

// t=1: Ядро 0: y=1  
//   → Store Buffer: [x=1, y=1]

// t=5: Ядро 1: r1 = y
//   → L1 cache: y=0 (инвалидация не пришла)
//   → r1 = 0

// t=6: Ядро 0: Store Buffer начинает выталкивать x=1
//   → RFO запрос на шину

// t=10: Ядро 1: r2 = x  
//   → L1 cache: x=0 (инвалидация в Event Queue)
//   → r2 = 0

// t=20: Инвалидации доходят до ядра 1
//   → попадают в Event Queue

// t=50: Ядро 1 обрабатывает Event Queue
//   → L1 обновляется: x=1, y=1

// Результат: r1=0, r2=0 (оба прочитали старое!)
```

### 8.2. Исправление барьером

```cpp
// Ядро 0
x = 1;
std::atomic_thread_fence(std::memory_order_release);
// → DMB ISHST (ARM) или SFENCE (x86)
// → ждёт опустошения Store Buffer
y = 1;

// Ядро 1
int r1 = y;
std::atomic_thread_fence(std::memory_order_acquire);  
// → DMB ISHLD (ARM) или LFENCE (x86)
// → обрабатывает Event Queue
int r2 = x;  // теперь видит актуальное x
```

```

│ ЯДРО 0                                                         │
```

## Часть 9: Ключевые выводы

### 9.1. Иерархия причин проблем

```
Высокая скорость ядер (GHz)
    ↓
Необходимость кэшей (меньше latency)
    ↓
Разные кэши у разных ядер
    ↓
Протокол когерентности (MESI) — решает видимость
    ↓
Но MESI медленный (нужны очереди)
    ↓
Store Buffer + Event Queue — ускоряют, но ломают порядок
    ↓
Нужны барьеры памяти
```

### 9.2. Три уровня абстракции

| Уровень | Что определяет | Пример |
|---------|---------------|--------|
| **C++** | memory_order | `relaxed`, `acquire`, `release`, `seq_cst` |
| **Компилятор** | compiler barrier + инструкции | запрет перестановок, выбор `LDAR`/`STLR` |
| **Процессор** | барьеры + очереди | `DMB`, `MFENCE`, Store Buffer, Event Queue |

### 9.3. Золотое правило

> **Когерентность кэшей** (MESI) гарантирует, что все ядра **в итоге** увидят одинаковые значения.
> 
> **Барьеры памяти** гарантируют, в каком **порядке** эти значения становятся видны.
>
> **Очереди ядра** (Store Buffer, Event Queue) — это оптимизации, которые нарушают порядок ради производительности.

### 9.4. Практические советы

1. **По умолчанию:** используй `seq_cst` (проще, безопаснее)
2. **Для счётчиков/статистики:** `relaxed` (максимум производительности)
3. **Для флагов готовности:** `release` + `acquire`
4. **Никогда не делай:** смешивание relaxed с обычными операциями
5. **Всегда проверяй:** false sharing (кэш-линии)

### 9.5. Что нужно помнить про очереди

| Очередь | Направление | Почему важна | Как исправить |
|---------|------------|--------------|---------------|
| **Store Buffer** | Ядро → кэш | Записи видны с задержкой | Release барьер (опустошить) |
| **Event Queue** | Кэш → ядро | Чтения могут быть устаревшими | Acquire барьер (обработать) |
| **Load Buffer** | Кэш → регистры | Почти не влияет на порядок | (обычно игнорируется) |

## Приложение: Таблица быстрого доступа

### Что видит ядро?
```
без барьера:  L1 Cache (может быть устаревшим)
с LFENCE:     L1 Cache + Event Queue (актуально)
с SFENCE:     Store Buffer опустошён (записи видны другим)
с MFENCE:     и то, и другое (полный порядок)
```

### Какие барьеры нужны?
| Хочу | Использую |
|------|-----------|
| Запретить перестановку store-store | `#StoreStore` (release) |
| Запретить перестановку load-load | `#LoadLoad` (acquire) |
| Гарантировать порядок production-consumer | `release` + `acquire` |
| Полный глобальный порядок | `seq_cst` |

### Архитектуры:
| Архитектура | Сила модели | Нужны ли барьеры? |
|-------------|-------------|-------------------|
| x86 | Сильная (TSO) | Только `MFENCE` для StoreLoad |
| ARM | Слабая | Все барьеры (DMB всех видов) |
| POWER | Очень слабая | Много барьеров + dependency |
| RISC-V | Слабая (RVWMO) | Барьеры (FENCE) |
