**Rate Limit** (ограничение скорости/частоты запросов) — это механизм контроля трафика, который ограничивает количество запросов, которое система (клиент, пользователь или IP-адрес) может выполнить за определенный промежуток времени.

### Зачем это нужно?

1.  **Защита от DDoS-атак и брутфорса:** Злоумышленники не смогут бесконечно долго стучаться в сервер, пытаясь подобрать пароль или положить его нагрузкой.
2.  **Предотвращение перегрузки сервера (Noisy Neighbors):** Один неаккуратный клиент (или баг в коде) не сможет положить сервис для всех остальных, отправив 10 000 запросов в секунду.
3.  **Честное распределение ресурсов:** Бесплатные или дешевые тарифы API обычно имеют низкий лимит. Хочешь больше — плати.
4.  **Борьба с парсингом:** Сайты ограничивают количество просмотров страниц в минуту, чтобы их контент не скопировали слишком быстро.
5.  **Экономика (монетизация):** Это основа многих бизнес-моделей API (например, условно: 1000 запросов в месяц — бесплатно, дальше — деньги).

### Основные алгоритмы Rate Limiting

Существует несколько классических алгоритмов реализации rate limit. Выбор зависит от задачи: нужно ли сглаживать пики или просто рубить поток.

#### Fixed Window Counter (Фиксированное окно)
Время разбито на отрезки (например, минуты: 12:00:00 — 12:00:59).
*   **Принцип:** В каждой минуте есть счетчик. Пришел запрос — увеличили счетчик. Как только счетчик достиг лимита (например, 100), все остальные запросы до конца этой минуты блокируются.
*   **Проблема (Краевое условие):** В 12:00:59 можно сделать 100 запросов, и в 12:01:00 можно сделать еще 100. В итоге за 2 секунды пройдет 200 запросов, что может временно перегрузить систему.
#### [[Rate Limit Token Bucket]] (Лексемное ведро) — Самый популярный
Представьте ведро, в которое падают токены (разрешения) с постоянной скоростью (например, 10 токенов в секунду). Объем ведра ограничен (например, максимум 100 токенов).
*   **Принцип:** Чтобы обработать запрос, нужно достать токен из ведра. Если токены есть — запрос проходит, если нет — получает ошибку (обычно `429 Too Many Requests`).
*   **Плюсы:** Позволяет обрабатывать небольшие всплески трафика (если ведро накопило токены). Прост в реализации.
*   **Где используется:** Часто в сетевом оборудовании и API-шлюзах.

#### [[Rate Limit Leaky Bucket]](Дырявое ведро) — Сглаживание
Похоже на Token Bucket, но работает наоборот. Это очередь (ведро) с дырочкой.
*   **Принцип:** Запросы поступают в ведро. Если ведро заполнено, лишние запросы отбрасываются. А снизу запросы «вытекают» (обрабатываются) с фиксированной постоянной скоростью.
*   **Плюсы:** Гарантирует **идеально равномерную** обработку запросов, отлично сглаживает пики нагрузки.
*   **Минусы:** Может вызывать задержки, так как запросы ждут своей очереди.

#### [[Rate Limit Sliding Window Log]] (Скользящее окно с логом)
Решение проблемы фиксированного окна.
*   **Принцип:** Для каждого пользователя хранятся временные метки его запросов (обычно в Redis). Когда приходит новый запрос, мы смотрим, сколько запросов было за последние, скажем, 60 секунд, отсекая старые метки.
*   **Плюсы:** Очень точное ограничение, без рывков.
*   **Минусы:** Требует больше памяти (хранить историю) и вычислительных ресурсов (нужно перебирать метки).

#### Sliding Window Counter (Скользящее окно со счетчиком) — Компромисс
Гибрид Fixed Window и Sliding Log. Используется в крупных распределенных системах.
*   **Принцип:** Держит счетчики для текущего и прошлого окна и рассчитывает примерное количество запросов в текущем скользящем окне по формуле взвешенной суммы.
*   **Плюсы:** Очень производительно и почти так же точно, как Sliding Log.
