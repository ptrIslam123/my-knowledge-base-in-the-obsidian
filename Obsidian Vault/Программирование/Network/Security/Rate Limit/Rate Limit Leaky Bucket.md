### Аналогия
Представь ведро с маленькой дырочкой на дне. Ты можешь выливать воду в ведро с любой скоростью (хоть ведром за раз), но **вытекает** вода только с постоянной скоростью через дырочку. Если ведро переполняется — вода выплескивается через край и теряется.

В терминах запросов:
- **Ведро** — это буфер (очередь).
- **Вода** — это входящие запросы.
- **Дырочка** — это скорость обработки запросов.
- **Переполнение** — запросы, которым отказали в обслуживании (429).

---

### Формальное описание алгоритма

Алгоритм оперирует двумя параметрами:

1.  **Bucket Size (b):** Максимальный размер очереди (буфера). Сколько запросов может ждать обработки одновременно.
2.  **Leak Rate (r):** Скорость, с которой запросы "вытекают" из ведра (обрабатываются). Например, 10 запросов в секунду.

**Жизненный цикл:**

1.  **Инициализация:** Ведро (очередь) создается пустым.

2.  **"Протекание" (Leaking):** С постоянной скоростью (каждые N миллисекунд) из ведра извлекается 1 запрос и отправляется на обработку. Если ведро пусто, ничего не происходит.

3.  **Потребление (Поступление запроса):**
    *   Приходит новый запрос.
    *   Система проверяет, есть ли свободное место в ведре (текущий размер очереди < Bucket Size).
    *   **Если ДА (место есть):** Запрос помещается в очередь (ведро). Он будет обработан, когда подойдет его очередь (со скоростью Leak Rate).
    *   **Если НЕТ (очередь заполнена):** Запрос отклоняется. Вода переполнила ведро и выплеснулась.

---

### Ключевое отличие от Token Bucket

Это важно понять, потому что эти алгоритмы часто путают:

| Характеристика | Token Bucket | Leaky Bucket |
| :--- | :--- | :--- |
| **Что хранится?** | Токены (разрешения) | Запросы (или задачи) |
| **Форма очереди** | Нет очереди. Либо есть токен сейчас, либо нет. | Есть очередь (FIFO). Запросы ждут. |
| **Выходной поток** | Не гарантирован. Может быть всплеск, если накопились токены. | **Строго постоянный.** Всегда `r` запросов в секунду. |
| **Входной поток** | Можно лить с любой скоростью, но если нет токенов — отказ. | Можно лить с любой скоростью, но если очередь заполнена — отказ. |

### Leaky Bucket математически

В реализации Leaky Bucket обычно хранят два значения:
1.  **Размер очереди** (сколько запросов сейчас ждут).
2.  **Время последнего "вытекания"** (когда последний раз обрабатывали запрос).

Псевдокод (упрощенный):
```python
# Состояние ведра
queue_size = 0
last_leak_time = now()
leak_rate = 10 # запросов в секунду
bucket_size = 50 # максимум мест в очереди

def allow_request():
    now = now()
    
    # Сначала "вытекаем" (освобождаем место) за прошедшее время
    time_passed = now - last_leak_time
    
    # сколько запросов должно было уйти
    leaked = time_passed * leak_rate
    
    # уменьшаем очередь, но не ниже 0
    queue_size = max(0, queue_size - leaked)
    last_leak_time = now
    
    # Проверяем, есть ли место для нового запроса
    if queue_size < bucket_size:
        # Место есть - ставим в очередь
        queue_size = queue_size + 1
        return True  # Запрос принят (будет обработан позже)
    else:
        # Места нет - отказ
        return False  # Запрос отклонен
```

### Где используется Leaky Bucket?

1.  **Сетевые устройства (роутеры, коммутаторы):** Классическое применение. Пакеты приходят с любой скоростью, но уходят в канал с фиксированной пропускной способностью.
2.  **Очереди задач (Task Queues):** Например, фоновые задачи ставятся в очередь (ведро), а воркеры забирают их с постоянной скоростью (дырочка).
3.  **Защита нижестоящих сервисов:** Если твой сервис вызывает внешний API, у которого жесткий лимит (например, 100 запросов в минуту), ты ставишь Leaky Bucket перед вызовом, чтобы не превысить лимит и не получить бан.

### Почему не всегда используют Leaky Bucket для API?

Leaky Bucket создает **задержку (latency)**. Запрос не обрабатывается сразу, а становится в очередь.

- **Token Bucket:** Запрос либо обрабатывается немедленно, либо получает отказ.
- **Leaky Bucket:** Запрос может быть принят, но клиент будет ждать ответа столько, сколько стоит в очереди.

Для интерактивных API (веб-сайты, мобильные приложения) задержка критична. Пользователь не хочет ждать 5 секунд, он хочет либо быстрый ответ, либо быструю ошибку, чтобы попробовать позже.

Поэтому Leaky Bucket чаще используют:
- Внутри систем (очереди задач).
- На сетевом уровне.
- Там, где важна **равномерность** любой ценой.

### Итог

**Leaky Bucket** — это алгоритм, который гарантирует **абсолютно равномерную** скорость обработки запросов ценой возможных задержек (очереди).

Параметры:
- **Bucket Size:** Толерантность к всплескам (сколько запросов может встать в очередь).
- **Leak Rate:** Скорость обработки.
