**SR-IOV (Single Root I/O Virtualization)** — это аппаратная технология виртуализации, которая позволяет одному физическому устройству PCIe (например, сетевой карте) представляться операционной системе как несколько отдельных устройств. В DPDK это один из самых мощных способов достичь максимальной производительности сети в виртуализированных средах.

###  Как это работает

Технология базируется на двух ключевых понятиях:

1.  **PF (Physical Function)** — это "главная" функция физического устройства. Она управляет всем устройством, может создавать и настраивать VF, обновлять прошивку и выполнять другие административные задачи. В DPDK это обычно основной порт (`rte_eth_dev`), который видит приложение.

2.  **VF (Virtual Function)** — это "легковесные" функции, которые создаются из PF. Каждая VF представляет собой самостоятельное сетевое устройство со своим:
    *   Уникальным MAC-адресом
    *   Выделенными аппаратными очередями (RX/TX)
    *   Собственной памятью для дескрипторов
    *   Возможностью обрабатывать прерывания

Главная особенность: VF — это **полноценное аппаратное устройство**, а не программный эмулятор. Драйвер VF напрямую общается с сетевым адаптером, минуя гипервизор.

---
### Техническая суть: PF и VF — это ОДНА микросхема

Самое важное, что нужно понять: **PF и VF — это не два разных устройства**. Это **одна и та же физическая микросхема** (NIC), но с разными **уровнями доступа** к её внутренним ресурсам.

Представьте, что сетевая карта — это **большой завод** с множеством станков (очередей). 
*   **PF** — это **директор завода**. У него есть доступ к любому станку, он может менять настройки, включать/выключать линии, видеть всё производство.
*   **VF** — это **начальник цеха**. Ему выделили **конкретные станки (очереди)**. Он работает только с ними, не видит, что делают в других цехах, и не может менять глобальные настройки завода.

---

### Очередь (RX/TX) в NIC

**Очередь** — это просто **кольцевой буфер (ring buffer) в памяти сетевой карты**, куда она складывает пакеты, пока их не заберет драйвер (или наоборот, куда драйвер кладет пакеты для отправки).

У карты есть **фиксированное количество аппаратных очередей** (например, 128). Каждая очередь имеет свой уникальный номер.

**Когда приходит пакет:**
1.  NIC смотрит на его заголовки (MAC-адрес, VLAN, RSS-хеш).
2.  На основе правил (которые настроил PF) она решает: **в какую очередь RX положить этот пакет?**
3.  Драйвер (или приложение DPDK) читает пакеты только из **своих** выделенных очередей.

---

### Как работает разделение через PF и VF?

**Разделение происходит не через создание новых очередей, а через РАЗДАЧУ существующих аппаратных очередей между PF и VF.**

#### Схема на примере карты с 16 очередями:

**Без виртуализации (только PF):**
```
Физическая NIC (16 очередей)
├── PF (Function 0) — полный доступ ко всем 16 очередям (0-15)
└── (нет VF)
```
Все пакеты приходят в очереди 0-15, драйвер PF читает их все.

**С включенным SR-IOV (PF + VF):**
```
Физическая NIC (16 очередей)
├── PF (Function 0) — управляет картой, но обрабатывает ТОЛЬКО очереди 0-7 (8 штук)
│   (например, для трафика управления хостом)
├── VF 1 (Function 1) — имеет доступ ТОЛЬКО к очередям 8-11 (4 штуки)
│   (можно отдать приложению DPDK или ВМ №1)
├── VF 2 (Function 2) — имеет доступ ТОЛЬКО к очередям 12-13 (2 штуки)
│   (можно отдать ВМ №2)
└── VF 3 (Function 3) — имеет доступ ТОЛЬКО к очередям 14-15 (2 штуки)
    (можно отдать ВМ №3)
```

**Важнейший нюанс:** Очереди **физически** существуют в NIC. VF не создает новые очереди. PF просто **"отдает"** (маппит) часть своих очередей каждой VF. 
 
PF **имеет доступ ко ВСЕМ очередям** (16 штук), потому что он директор.
Но когда включен SR-IOV, PF **добровольно ограничивает себя** и говорит: "Я буду обрабатывать только очереди 0-7, а очереди 8-15 я отдам VF".

VF **не создает новые очереди**. VF получает **право владения** (ownership) над конкретными, уже существующими аппаратными очередями.

Как это выглядит в железе:
- В регистрах NIC есть таблица, которая говорит: "Очередь с номером X принадлежит функции Y".
- Когда драйвер VF пытается читать из очереди 8, аппаратура разрешает это.
- Когда драйвер PF пытается читать из очереди 8, аппаратура тоже разрешит (потому что PF — главный).
- Но драйвер VF **не может** читать из очереди 0 — аппаратура выдаст ошибку.

### Изоляция и безопасность

Изоляция обеспечивается на **аппаратном уровне** внутри микросхемы NIC:

1.  **Аппаратный Firewall/MMU:** В NIC есть внутренний менеджер памяти, который проверяет, имеет ли данная функция (PF или VF) доступ к запрашиваемой очереди или области памяти.
2.  **Независимые DMA-каналы:** Каждая VF имеет свой выделенный канал прямого доступа к памяти (DMA) хоста. Пакеты из VF1 идут в свой буфер в RAM хоста, VF2 — в свой. Они физически не могут перезаписать память друг друга, потому что NIC настроена раздавать разные адреса памяти.
3.  **Аппаратное кэширование тегов:** Каждый пакет в очереди помечается тегом функции-владельца. Если драйвер VF попытается прочитать пакет из чужой очереди, аппаратура просто вернет ошибку (или проигнорирует запрос).

### Основные преимущества

*   **Максимальная производительность:** Трафик VF идет напрямую в виртуальную машину (ВМ), обходя программный сетевой стек гипервизора и виртуальный коммутатор (например, Open vSwitch). Это дает производительность, близкую к нативной (native performance).

*   **Аппаратная изоляция:** Ошибки или атаки в одной ВМ не могут повлиять на работу других ВМ, так как каждая использует свои аппаратные ресурсы.

*   **Аппаратное ускорение:** Все оффлоады, поддерживаемые NIC (TSO, checksum, RSS), доступны каждой VF напрямую.

* DPDK использует концепцию **"Port Representors"**[](https://doc.dpdk.org/guides-25.11/prog_guide/ethdev/switch_representation.html#port-representors%5Cn) . В режиме "Controlled SR-IOV" приложение на хосте может управлять и направлять трафик между VF и физическим портом так, как будто оно управляет настоящим коммутатором. Для этого используются "VF representors" — виртуальные DPDK-порты, которые представляют собой интерфейс для управления VF. Это позволяет, например, перенаправлять трафик с одного VF на другой без участия CPU самого хоста[](https://doc.dpdk.org/guides-25.11/prog_guide/ethdev/switch_representation.html#port-representors%5Cn)

### Как это реализовано в DPDK

В DPDK поддержка SR-IOV отображается в структуре данных порта. Атрибут `sriov` в `rte_eth_dev_data` содержит информацию о созданных VF, такую как:
*   `nb_vfs`: количество созданных виртуальных функций.
*   Конфигурация каждой VF (состояние, MAC-адрес, VLAN, настройки очередей).

**Типичный сценарий использования:**

1.  **На хосте:** Приложение DPDK работает на PF (или на одном из PF) и управляет сетевым адаптером.
2.  **Создание VF:** Приложение создает VF с помощью вызовов DPDK (которые, в свою очередь, используют системные интерфейсы, такие как `ioctl` в Linux или API драйвера). Например: `rte_eth_dev_vf_set_vf_rate_limit` или похожие функции для настройки.
3.  **Назначение VF:** Созданные VF "пробрасываются" (passthrough) в виртуальные машины с помощью гипервизора (KVM, VMware и т.д.).
4.  **Внутри ВМ:** Гостевая ОС загружает драйвер для VF (например, `ixgbevf` для карт Intel X710). Этот драйвер взаимодействует с VF так, как будто это обычная физическая сетевая карта. Если внутри ВМ запущено приложение DPDK, оно может открыть этот порт как обычный DPDK-порт и работать с ним на полной скорости.
