**SNI (Server Name Indication)** — это расширение протокола **TLS (Transport Layer Security)**, которое позволяет клиенту (например, веб-браузеру) указать, к какому именно доменному имени он пытается установить защищённое соединение, ещё **до завершения TLS-рукопожатия** .

### Зачем это нужно?
Раньше один IP-адрес мог обслуживать только один TLS-сертификат. Это создавало проблему при размещении нескольких HTTPS-сайтов на одном сервере (виртуальный хостинг): сервер не знал, какой сертификат предъявить клиенту, потому что имя хоста передаётся только на уровне HTTP — **после** установки TLS-соединения.

SNI решает эту проблему: клиент включает имя целевого хоста прямо в начальное сообщение **ClientHello** TLS-рукопожатия. Это позволяет серверу выбрать правильный сертификат и корректно завершить установку безопасного соединения .

### Ключевые особенности:
- Позволяет **размещать множество HTTPS-сайтов на одном IP-адресе** без конфликтов сертификатов .
- Поддерживается практически всеми современными браузерами и ОС (начиная с Windows Vista, OpenSSL 0.9.8f и т.д.).
- Является **обязательным** для эффективного использования CDN, облачных сервисов и shared hosting’а .

### **Как технически работает:**
1. Клиент инициирует TLS ClientHello.
2. В расширении (`extension`) `server_name` указывает имя хоста в открытом виде.
3. Сервер получает это имя, находит соответствующий сертификат и продолжает рукопожатие.

**Пример (упрощенный):**
```
ClientHello {
  ...
  Extensions: [
    server_name: "example.com"
  ]
}
```

### **Важные особенности и проблемы:**
* **SNI передается в открытом виде** — это главный недостаток. Любой наблюдатель (провайдер, государство, хакер) видит, к какому домену вы подключаетесь, даже если содержимое зашифровано.
* **Обязателен для современного интернета** — без него невозможен виртуальный хостинг HTTPS-сайтов.
* **Поддержка:** Требуется поддержка как на стороне клиента, так и сервера. Все современные ОС и браузеры поддерживают.

### **ESNI и ECH (будущее):**
* **ESNI (Encrypted SNI)** — первая попытка шифрования SNI с помощью ключей из DNS.
* **ECH (Encrypted Client Hello)** — развитие ESNI в TLS 1.3, шифрует **весь ClientHello**, включая SNI. Сертификат сервера используется для шифрования. Это решает проблему утечки метаданных.

---

**Encrypted Client Hello (ECH)** — это современное расширение протокола **TLS 1.3**, разработанное для **полного шифрования метаданных клиентского приветствия (ClientHello)**, включая такие чувствительные поля, как **SNI (Server Name Indication)** и **ALPN (Application-Layer Protocol Negotiation)**. Это решение пришло на смену более ранней экспериментальной технологии **ESNI (Encrypted SNI)** и устраняет ключевую уязвимость приватности в TLS: утечку имени запрашиваемого домена в открытом виде.

---

## Исторический контекст: от ESNI к ECH

- **ESNI (Encrypted SNI)** — первоначальная попытка зашифровать только поле SNI в рамках TLS 1.3. Она использовала DNS-записи типа `TXT` или `HTTPS` для публикации **публичного ключа сервера**, который клиент использовал для шифрования SNI.
- Однако ESNI имел ограничения:
  - Шифровалось **только SNI**, остальные поля (например, ALPN, список поддерживаемых шифров) оставались открытыми.
  - Сложность развёртывания и несовместимость с некоторыми middlebox’ами.
- В результате IETF заменил ESNI на **ECH**, который шифрует **весь внутренний ClientHello**, а не только SNI .

---

## Как работает ECH

ECH использует **двухуровневую структуру ClientHello**:

### 1. **Outer (внешний) ClientHello**
- Отправляется в открытом виде.
- Содержит **заглушку** вместо реального имени сервера (например, `cloudflare-esni.com`).
- Может содержать общие параметры, но **не чувствительные данные**.
- Используется для совместимости с прокси, балансировщиками и старыми middlebox’ами.

### 2. **Inner (внутренний) ClientHello**
- Полностью **зашифрован** с помощью **HPKE (Hybrid Public Key Encryption)**.
- Содержит **настоящее SNI, ALPN, список шифронаборов, расширения и т.д.**
- Расшифровывается **только целевым сервером**, у которого есть соответствующий **приватный ключ**.

Ключ для шифрования публикуется в **DNS-записи типа `HTTPS`** (ранее использовалась `TXT`), например:

```dns
example.com. IN HTTPS 1 . alpn="h2" ech="M...base64..."
```

Клиент получает этот ключ через DNS перед установкой TLS-соединения .

---

## Криптографическая основа: HPKE

ECH опирается на **HPKE (RFC 9180)** — современный стандарт гибридного шифрования с открытым ключом, сочетающий:
- **KEM (Key Encapsulation Mechanism)** — например, DHKEM с X25519.
- **AEAD (Authenticated Encryption with Associated Data)** — например, AES-GCM или ChaCha20-Poly1305.

Это обеспечивает:
- **Forward secrecy** (если используется ephemeral KEM).
- **Аутентификацию** и **целостность** зашифрованного ClientHello.
- Высокую производительность и модульность .

## Поддержка и развёртывание

- **Браузеры**:
  - **Firefox**: поддержка ECH включена по умолчанию с версии 117+ (2023).
  - **Chrome**: экспериментальная поддержка, но пока не включена по умолчанию.
- **Серверы**:
  - **Cloudflare**: один из первых провайдеров, внедривших ECH глобально.
  - **Nginx**, **Apache**: пока требуют патчей или сторонних модулей.
- **DNS**: требуется поддержка **DNS-over-HTTPS (DoH)** или **DNS-over-TLS (DoT)** для защиты самого запроса ключа ECH от прослушивания .

## Преимущества ECH

| Проблема без ECH | Решение с ECH |
|------------------|----------------|
| SNI виден провайдеру, фаерволу, DPI-системам | Полное скрытие SNI и других метаданных |
| Цензура может блокировать по домену | Блокировка становится сложнее (требуется глубокий анализ или блокировка всего IP) |
| Утечка информации о поведении пользователя | Повышение приватности на уровне транспорта |

---

## ⚠️ Ограничения и вызовы

1. **Зависимость от DNS**: если злоумышленник контролирует DNS или использует поддельные ответы, он может подменить ECH-ключ.
2. **Middlebox interference**: корпоративные прокси или DPI-системы могут ломать соединения, если не понимают ECH.
3. **Fallback-риски**: при ошибке расшифровки сервер может запросить повторное соединение без ECH — это потенциальный вектор атаки (downgrade).
4. **IP-адрес всё ещё идентифицирует сервис**: ECH не скрывает IP назначения, только имя хоста.

---

## Будущее

ECH официально стандартизирован в **IETF как RFC 8446bis** (обновление TLS 1.3) и рассматривается как **ключевой компонент "приватного интернета"**. В перспективе он может стать обязательным для всех HTTPS-соединений, особенно в условиях роста DPI и государственной цензуры.

> «ECH is a mechanism for Transport Layer Security version 1.3 (TLS 1.3) that is designed for encrypting ClientHello messages under a server public key» .
